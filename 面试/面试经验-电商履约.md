3. mq事件消费积压：
      解决方式：
               3.1. 分层限流. 发送端(业务规则分优先级发送) -→MQ 层(增加不同优先级队列) -→消费端(保护自己防崩溃). 
               3.2. 自动调度. 实时监控数据(感知mq的堆积情况) --> 多维度加权决策 --> 规则引擎+动态配置 --> 错峰 + 资源倾斜 调度
               3.3. 优先级区分，让 “非核心请求限流 / 延迟”，“核心请求优先通过 + 快速消费”，积压作为临时缓冲而非长期方案

### 电商履约的领域拆分问题
1. 理清履约场景的 “核心业务活动” 和 “上下文边界”—— 这是服务拆分的前提。以“业务语义” 为核心，通过 “子域 - 限界上下文 - 微服务” 的映射，实现高内聚、低耦合的服务拆分
        核心子域动包括：履约计划制定，虚拟履约， 实物履约， 线下老师履约，履约状态管理， 履约异常管理.
2. 为什么要这么拆分， 依据是什么
        2.0. 解决教育电商履约大单体的核心痛点(逻辑混乱, 故障扩散, 扩展困难)
        2.1. 业务依据
                 2.1.1.  (DDD 核心原则：限界上下文的 “边界清晰性”) 业务语义不重叠，职责不交叉： 虚拟履约(权限，账号)和实物履约(物流，库存)差异巨大，履约状态服务的核心是 “状态聚合与查询”，不参与具体履约执行
                 2.1.2.  业务流程的 “自然断点”. 履约的流程是 “制定方案→分类型执行→状态跟踪→异常处理”，每个环节都是自然断点. 方案是前置决策，“执行” 是后置动作
        2.2. 数据自治性（DDD “聚合根” 思想）
                   每个服务管理自己的核心数据，避免跨服务查库：
        2.3. 康威定律：服务拆分匹配团队结构 康威定律指出 “系统设计反映团队结构”：
                  按服务划分团队：虚拟履约团队、实物履约团队、线下履约团队，每个团队负责对应服务的开发 / 维护；
                  团队内沟通成本低，跨团队通过 “领域事件” 协作，无需频繁联调，效率提升。
3. 拆分后的效果怎么样
       3.1. 业务效果：履约效率提升(物流时间，虚拟开通时间)，履约体验优化：用户在 APP 可实时查看， 业务扩展性增强(新增履约类型无需计划变更)
       3.2. 技术效果：可用性提升：整体履约链路的 SLA； 迭代速度加快(各履约独自迭代)； 资源利用率优化：虚拟履约服务是 CPU 密集型（权限计算），配高 CPU 机器；实物履约服务是 IO 密集型（对接物流 API），配高 IO 机器，避免资源浪费


#### 常见问题：限界上下文划分 “过粗” 或 “过细”
1. 影响：
      过粗：上下文内代码量庞大，团队维护效率低；业务规则变更时，牵一发而动全身，风险高。
      过细：跨上下文依赖爆炸，接口调用链长，性能损耗大；分布式事务、数据一致性问题突出。
2. 解决方向：
       3.1. 用 “事件风暴” 梳理边界：
               通过 “命令→事件→聚合” 的链路，识别业务流程中 “职责内聚” 的模块（如 “支付” 相关的命令 / 事件 / 聚合都属于 “支付上下文”）。
       3.2. 遵循 “高内聚、低耦合” 原则：
               一个上下文内的所有组件（聚合、领域服务）应服务于 “同一个业务目标”（如 “库存上下文” 的目标是 “保障库存准确性与可用性”）。
       3.3. 参考 “组织架构”：
               康威定律（Conway's Law）指出 “系统设计反映组织沟通结构”，若公司内有 “订单团队”“支付团队”，可对应划分 “订单上下文”“支付上下文”，减少跨团队协作成本。

### (电商履约-限界上下文划分问题)履约计划和履约状态是否是同一个限界上下文呢，是否可以合并成一个
1. 要做判断，核心是回归DDD 限界上下文的本质 ——“业务语义边界是否清晰、核心职责是否内聚且不重叠”。
      1.1. 核心职责： (定方案” 和 “盯进度” 是两回事).
                1.1.1. 业务逻辑焦点： 计划是解析订单，匹配规则，输出方案； 状态是接受、聚合、查询履约状态。
                1.1.2. 业务价值导向： 计划是关注方案正确性， 状态是关注履约进度 “看得见”，老师用户都可以看到履约到哪一步了
      1.2. 修改一个上下文的逻辑时，是否需要理解另一个上下文的业务细节
                1. 限界上下文的 “独立”，体现在 “业务决策逻辑的隔离”，而非 “业务流程的隔离” 
                      (比如计划因为用户申请或者规则改变等，在计划上下文内部就决定了。 但计划改了，状态也要跟着更新这是业务流程)
      1.3. 数据依赖与产出：
                 1. 计划依赖订单，产出计划表；  状态是依赖各履约方的状态，产出快照，变更日志表。
2. 为什么不能合并？—— 合并会导致 “职责混杂”，埋下业务和技术隐患
      2.1. 技术层面： 履约计划：是 “低频、计算密集型” 服务 ； 履约状态：是 “高频、IO 密集型” 服务
      2.2. 业务层面：(业务层面：职责混乱，影响迭代效率)
             2.2.1. 开发 “规则优化” 时，需担心误改 “状态聚合” 的代码；
             2.2.2. 开发 “状态展示” 时，需理解 “履约方案决策” 的复杂逻辑（如为什么这个订单会生成物流任务），学习成本高；
             2.2.3. 测试时需覆盖 “决策 + 状态” 的全链路，测试用例翻倍，上线周期拉长（原本各服务可并行迭代，合并后只能串行）。
3. 补充：两者的协作方式 —— 低耦合，而非强绑定
      3.1. 虽然不能合并，但履约计划和履约状态存在 “业务关联”（计划是状态的 “源头”，状态是计划的 “结果反馈”, 两者都需要感知业务内容），DDD 中通过 “领域事件” 实现低耦合协作，
      3.2. 区分订单实体和订单状态， 这种计划存在多种并行的执行， 状态也是多种子场景的聚合， 与订单的单一场景不同。(订单的核心价值是 “交易闭环记录”,合理设计：“支付态 + 履约结果态” 双维度组合)


### 履约计划和履约状态 能否放到同一个微服务里呢，什么时候可以拆分呢？
> DDD的限界上下文是逻辑边界，微服务是物理边界。在资源有限、功能尚不复杂时，将多个逻辑上下文部署在同一个物理服务内，是一种标准的“降级”策略，可以显著降低运维成本。
1. 虽然不是一个上下文，但是可以放到一个微服务里，不同的component就可以。尽管在同一个服务内，它们依然通过领域事件进行异步解耦
2. 拆分时机参考：
       2.1 团队结构
       2.2.发布频率
       2.3. 技术栈/使用资源
       2.4. 性能与扩展
       2.5. 故障隔离， 一个服务引起的故障是否可接受全部不可用




### 常见问题：聚合根设计不当（过大 / 过小 ）
> 聚合根是聚合的核心，承担着维护聚合内一致性、界定事务边界、封装领域规则的关键职责。
1. 聚合根过大：
      1.1. 原因： 未理解聚合的核心作用是 “保证事务内的数据一致性”—— 只有 “必须同时修改、且需强一致性” 的对象才应放入同一聚合。
      1.2. 带来问题： 并发冲突加剧， 查询效率低下，不同聚合根的生命周期不一致带来问题(比如供货商系统中的排期和订单耦合)
2. 聚合根过小：
      2.1. 原因： 过度追求 “聚合轻量化”，忽视 “业务概念的完整性”；
      2.2. 带来问题：
               跨聚合事务复杂性， 
               领域模型碎片化，过小的聚合会导致模型无法体现业务对象间的核心关联（例如将 “订单” 和 “订单项” 拆分为两个聚合，违背 “订单项依赖订单存在” 的业务常识），降低模型的可理解性。
3. 聚合根职责模糊，破坏封装性(聚合根的核心职责是 “对外暴露聚合的行为，隐藏内部实现”。)
      1. 聚合根成为 “贫血模型”：
               仅作为数据容器，无业务逻辑，将本应属于聚合根的规则（如订单状态流转校验）放到外部服务中，导致领域逻辑分散
      2. 允许外部直接访问聚合内对象
               例如聚合根提供getItems()方法暴露内部订单项集合，外部可直接调用add()/remove()修改，绕过聚合根的校验逻辑（如 “订单已支付后不能修改订单项”），破坏封装性。
4. 错误的聚合根引用，导致依赖混乱(聚合根之间的引用需遵循 “只引用其他聚合根的 ID，而非实体本身” 的原则（避免跨聚合紧耦合）)
     1. 直接引用其他聚合的内部实体：例如 “订单聚合根” 直接持有 “商品聚合” 中 “商品详情实体” 的引用，当商品聚合的内部结构变化时（如商品详情新增字段），会直接影响订单聚合，增加耦合度。
     2. 聚合根之间形成循环依赖：例如 “订单” 引用 “用户”，“用户” 又引用 “订单”，导致模型复杂度上升，序列化、持久化时可能出现异常。
5. 数据库表设计困难，违背领域意图
     1. 过大的聚合会导致 表 的查询接口臃肿（需支持 “只加载聚合部分数据” 的不合理需求），违背 “Repository 操作整个聚合” 的原则。
     2. 过小的聚合会导致需要多张表协作完成一个业务操作（如创建订单需调用订单 Repository、库存 Repository、优惠券 Repository），增加代码复杂度，且难以体现业务操作的原子性。


### (电商履约-聚合根设计不当) 履约订单是否包含履约计划？ 
> 两大核心原则：“聚合内实体 / 值对象生命周期一致、紧密关联” 和 “聚合根仅维护聚合内的业务一致性，不承担超出边界的职责”
应该包含，否则会导致聚合根过小，
- 修改履约订单也要修改履约计划，是事务强一致性的。 生命周期强相关(取消则全部需要取消)。 而不是弱相关(不应包含状态，因为更新频率不一致)。
- 查询履约订单时，不需要跨聚合就能获取履约的详细信息。


### 当在进行 DDD 领域拆分时，遇到某个业务逻辑或功能“既可以放到 A 服务，也可以放到 B 服务”的情况，怎么解决：
> 比如 视频推荐类的ai作业，作业不应该关注视频课的东西， 推荐系统和视频课系统是数据互通的， 作业在中间只起桥梁作业，不关心json的具体格式
> 比如 relation关系不应该存在exerciseRecord服务中，该放在homework中。(这里是关注点分离原则)
> 4. 其他例子和方案
     4.1. 履约进度通知， 既能放「履约状态服务」，也能放「履约异常服务], 但是：业务语义内聚 —— 通知的本质是 “进度同步”，而非 “异常处理”，放状态服务。
     4.2. 实物履约前的「库存预检查」，但是：业务流程断点 ——“决策层” 做预筛，“执行层” 做最终确认，最终归属：「履约计划服务」（预检查）+「实物履约服务」（最终检查）
     4.3. 异常处理结果的「可视化展示」，最终归属：「履约状态服务」（聚合展示）+「履约异常服务」（存储详情）

1. 聚合根边界优先：
        聚合根是领域的 “核心实体”，承载了领域的核心业务规则和状态，所有功能都应围绕 “服务于哪个聚合根” 展开。
        判断功能是否属于某一域的 “核心聚合根”（如错题属于练习评估域的 “错题本” 聚合根，规则属于家长管控域的 “管控规则” 聚合根）
2. 业务闭环完整性：
        这个功能的核心目标是为了实现哪个服务的核心职责，是在哪个限界上下文中
        功能需融入某一域的 “核心职责闭环”（如作业学情报告的基础信息属于作业域的 “作业数据管理” 闭环，补弱建议属于学习路径域的 “个性化规划” 闭环），避免拆分后跨域调用频繁
3. 数据一致性成本：
         优先放在 “数据源头域” 或 “已有数据处理逻辑的域”（如错题同步放练习评估域，因练习评估域已有错题去重逻辑），减少数据冗余和跨域同步延迟。
4. 用户体验连贯性：
         若功能涉及用户操作（如管控规则、报告查看），优先放在 “用户主要交互域”（如时长提醒放家长管控域，因家长主要在管控模块操作），避免跨模块跳转。
5. 业务迭代频率： 
         把变化频率高的逻辑放在它的所属服务中，便于维护和演进
总结：
   DDD 的领域拆分不是 “一次性决策”，而是 “伴随业务演进的迭代过程”—— 关键是始终以 “业务领域” 为锚点，避免因短期技术便利偏离长期架构合理性。

### ddd领域拆分，不是各领域之间不依赖，而是治理依赖(即领域间的上下文映射)
1. 领域之间是有依赖的，否则业务无法完成， 比如订单和履约。 比如作业和ai每日练。 作业是天然依赖每日练的。这是业务流程。
2. 依赖治理，是指防止无序依赖，根据ddd划分，领域内部只处理自己的事件， 别的领域不关心内部细节，只通过领域间依赖进行交互。 
3. 尽量将依赖显示出来， 就像作业里面的业务参数，虽然作业不用理解，但是需要app将这些业务参数传递给各个业务里去理解， 这就是隐士依赖，需要app来处理
4. 处理ddd之间的依赖，就上下文交互，有几种方式(通过领域事件， 通过约定契约-接口，抽象基础服务)， 契约：比如作业系统增加场景配置能力，app不和各业务交互，只和作业交互，作业需要和各业务交互，获取结果扔给app。


### 常见问题 2：忽视 “最终一致性”，过度追求强一致性
1. 表现：
       跨聚合 / 跨上下文的操作（如 “订单确认→扣减库存→通知支付”）强行用分布式事务（如 Seata、2PC）保证强一致性，导致系统性能低下、可用性降低；或未处理 “部分成功” 的场景（如订单确认成功，但库存扣减失败，未触发回滚或补偿）。
2. 根源：
       未理解 DDD 的 “最终一致性” 思想 —— 聚合内保证强一致性（通过本地事务），跨聚合 / 跨上下文通过 “领域事件 + 补偿机制” 实现最终一致性；对分布式事务的 “成本”（性能、复杂度）认识不足。
3. 影响：
       分布式事务导致系统响应慢、并发低；2PC 等协议在网络异常时易出现 “阻塞”，可用性差；过度设计增加开发和维护成本。
4. 解决方向：
       聚合内强一致，跨聚合最终一致：① 聚合内的操作（如创建订单时添加订单项）用本地事务保证强一致；② 跨聚合操作（如订单确认→扣减库存）通过 “领域事件” 异步触发，下游服务失败时通过 “补偿事件” 重试（如库存扣减失败，发布InventoryDeductFailedEvent，订单服务接收后将订单状态回滚为 “待确认”）。
       避免分布式事务：优先用 “事件驱动 + 最终一致性” 替代分布式事务，仅在 “资金类核心场景”（如支付）考虑轻量级分布式方案（如 TCC）。




### 项目中如何进行扩容：
1. 第一步：诊断瓶颈 —— 明确 “要不要扩”“该扩哪”
     1. 核心监控指标（量化瓶颈， 单指标不行，需要多指标组合才能看出问题）： 
            1.1. cpu/线程池/内存等资源瓶颈； 
                      1.1.1. 应用计算资源瓶颈： CPU 使用率持续≥80%、Load Average≥CPU 核心数 ×1.5；线程池活跃数≥核心线程数 90%+ 任务排队
                      1.1.2. 同机器资源争抢瓶颈：服务器整体 CPU / 内存≥90%，单个服务资源占比超 80%；其他服务 RT / 错误率和高占用服务峰值同步波动
            1.2. 接口耗时上涨50%/qps超阈值/线程池队列持续上涨；
            1.3. 依赖资源出问题：mysql的cpu/线程池等出问题； redis满了， rpc队列超时等。
                      1.3.1. 本服务 CPU / 内存正常，但 RT 升高；依赖服务响应时间≥1s（较正常翻倍）、错误率≥0.5%
                      1.3.2. 数据库 IO 利用率≥80%、查询延迟≥500ms；缓存命中率下降 20%+、内存使用率≥90%；数据库连接池耗尽
     2. 业务触发场景（提前预判扩容需求）
            2.1. 开学季/运营活动等： 需提前 1-2 周扩容。
            2.2. 突发场景：流量骤增（如某课程突然爆火）、服务故障（单台机器下线导致负载不均），需紧急扩容。
2. 第二步：选型扩容类型 —— 明确 “怎么扩”（按优先级排序）
     升级硬件 / 微服务分层扩容 / 弹性扩容
