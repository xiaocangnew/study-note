### 库存问题
1. 库存扣减的几种模式： 下单直接扣库存不锁定、 下单锁库存支付扣库存；
2. 保证不超卖的机制
        2.1. lua脚本，保证检查更新是原子操作,  检查时还保证了幂等--同一个订单不会重复扣减，同一个订单需要先锁定，再扣减。(核心是获取锁定库存的redis和lua脚本的redis需要在同一个hash槽上)
        2.2. redis + 异步mq更新MySQL (redis主从切换导致库存回滚，怎么保证redis与mysql一致性)
                 2.2.1. Redis 层：从源头减少主从切换的数据丢失： redis强制主库只有在满足同步条件时才接受写操作，否则直接返回秒杀失败，从源头避免数据丢失(最少副本数量，最大主从延时)
                 2.2.2. 扣减与消息层：保证 Redis 扣减和 MQ 发送的原子性。 引入事务消息，耗时增加约一毫秒可接受， rocketmq百万级qps不受影响
                 2.2.3. 关键优化：Redis 扣减时记录「库存流水」。当 Redis 回滚后，可通过流水记录恢复正确的库存数据，避免数据不一致
                 2.2.4. 创建订单时，Redis 初步扣减库存 + MySQL 最终库存兜底， 防止超卖。(订单增加待确认状态， 只有当库存真的占上了，才变为待支付)
                 2.2.5. 分钟级/10秒级 校验redis和mysql中的库存。
                            2.2.5.1. 保证修复过程的正确性： 使用版本号，先查询mysql库存和版本号，对比redis不一致后，再此查询mysql库存和版本号，如果版本号一致，则修复；如果版本号不一致，则放弃本次修复。(以mysql数据为基准，保证整个过程的正确性)
        2.3. oceanBase 的库存更新并发是MySQL的3-5倍，但也无法应对秒杀的超高瞬时并发。
3. 两级缓存架构模式: 本地缓存 + redis + DB层。
        3.2. Db更新成功后发送mq， 本地缓存更新。
        3.3. 本地缓存使用场景(可以指定查询时是使用本地缓存，还是redis缓存)
                3.3.1. 读多写少场景：查询频率远高于更新频率
                3.3.2. 性能要求：降低延迟，提升吞吐
                3.3.3. 实时性要求不高：展示类查询可接受短时延迟
                3.3.4. 预检查场景：快速过滤明显无效的请求
4. 高并发下其他库存扣减方案
       4.0. (0 - 5k) mysql 行锁 / 乐观锁 直接更新库存
       4.1. (1 万～5 万 QPS )redis + 异步mq更新MySQL
       4.2. (10 万 QPS ) 引入本地缓存， mysql升级成oceanbase， mq单条消费升级批量消费，
       4.3. (单redis 20 万 QPS) 预生成秒杀资格码, 彻底避免高并发下的库存竞争。
5. 分布式锁在库存问题中的应用

### 购物车(核心场景，核心约束，挑战与风险，技术亮点)
1. 数据表结构
      1.1. cartItem -> cartCoupon -> cartItemCoupon, 不需要cart实体。
      1.2. 核心的存储字段： 状态， 价格，优惠信息
                 1.1.1. 价格必须存储(性能问题； 价格变化时可以给用户提示对比用；)
                 1.1.2. 优惠信息必须存储(性能问题；用户体验)
2. 存储选型
      2.1. 根据业务场景(增删改，价格变化上下架等)和技术需求(读写性能，数据一致性，持久化，过期策略等)， 使用redis + mysql。
3. 使用redis缓存后的问题：
      3.1. 数据一致性问题(mysql和redis 数据一致性)
                3.1.1. 写操作的一致性( 核心数据同步写=先写mysql，成功后写redis； 异步写=redis成功后发送mq更新mysql)
                3.1.2. 后台定时任务对比 Redis 与 MySQL 的购物车数据，修复不一致
                3.1.3. 读的不一致性(使用mysql和redis的版本号对比机制)
      3.2. 数据同步问题(商品价格变动，购物车如何感知)
                3.2.1. 差异化更新机制，平衡一致性和性能(实时强一致--主动推送影响面小的核心商品， 用户查看时才更新--延迟更新避免全量的性能风险 + 版本号校验降低查询数量)
                3.2.2. 分层保证一致性(商品加入购物车 -> 价格变动时推拉结合 -> 结算环节强校验兜底最终一致性保障)
      3.3. 缓存问题
                3.3.1. 缓存击穿，缓存穿透，缓存雪崩


### 电商场景中redis+本地 双缓存的场景和常见问题
1. 商品展示： 本地缓存top100热门商品 + redis 全量商品    (本地缓存承接 80% 的热门请求，Redis 作为兜底和分布式共享层，数据库仅处理缓存未命中和更新请求。)
2. 商品下单： 防超卖(本地缓存库存+redis库存) \ 限购(本地缓存「全局限购规则」+ redis 缓存「用户已购数量」)
3. 交易环节： 状态高频查询 (大促秒杀订单，一个订单短时间被查上百次，qps暴增。 单redis会浪费在非核心场景上)。  
         3.1. 本地缓存（ 5分钟内订单防爆内存 + 1-5 秒过期 + 发布/订阅删除本地缓存） + Redis（全量支付状态）。
         3.2. 使用redis 的发布订阅模式，相对于mq来说，稳定性低，但是是内存级操作，耗时更低，对于这种非核心数据是更轻量级的解决方案。
         3.3. 本地缓存只缓存支付中这种中间态（用户高频刷新的状态），支付成功后，可以直接走redis，因为支付成功的查询频率低。
         3.4. 发布/订阅时，可以通过只发布支付成功/失败事件，其他事件不操作，来降低删除缓存和缓存重建的频率，增强命中率。
         3.5. 缓存重建时做 “请求归并”：同一实例内避免重复查 Redis，保证redis整体qps可控。


### 如何解决复杂价格计算的高并发问题
1. 架构分层：解耦复杂链路，实现 “专服专做”
         1.1. 规则管理层 (规则定义、优先级配置、生效条件管理, 规则版本控制, 规则预校验避免互斥)
         1.2. 计算服务层 (单独拆分微服务， 接收下单请求，执行价格计算逻辑, 同步计算 + 异步降级（核心规则同步算，非核心异步补）)
                1.2.1. 计算路径优化：从 “实时全量计算” 到 “预计算 + 按需计算”
                         1.2.1.1. 提前拦截，降低无效请求调用
                         1.2.1.2. 分场景预计算：热门商品/固定规则，提前解析价格，常用组合，缓存到redis中
                         1.2.1.3. 规则简化：降低实时计算复杂度( 定义 “规则原子化组件”, 使用“组件编排” 实现复杂规则， 优先级剪枝防止无用逻辑)
                1.2.2. 并发控制与一致性保障：避免 “高并发下的脏数据”
                         1.2.2.1. 使用分布式锁防止原子问题
                         1.2.2.2. 非价格计算核心逻辑，使用mq异步处理。
                         1.2.2.3. 并行计算：利用多核资源提升吞吐
         1.3. 数据支撑层 (聚合价格计算所需的基础数据（商品价、优惠券、库存、会员等级等）)。 
                1.3.1. 读写分离 + 分库分表 + 数据冗余存储防止垮库调用
                1.3.2. 缓存加速层 
                        1.3.2.1. 用户等级、会员权益等变更频率低的数据：缓存久+主动失效 + 定时刷新兜底
                        1.3.2.2. 高频变更数据比如用户已购数量：不缓存 / 短过期 + 实时查询兜底
                  
   
### 拆单
拆分子订单的目的是让「每个子订单能独立完成发货、售后」，因此判断是否拆单，关键看商品是否满足 “三同” 履约条件（电商通用标准）：
- 同仓库（发货仓一致，避免跨仓合并发货增加成本）；
- 同物流类型（如普通快递、冷链、顺丰加急，物流方式不同无法合并）；
- 同售后规则（如是否支持 7 天无理由、是否定制商品，售后逻辑不同需单独管理）。
补充特殊维度：
 - 商品类型（虚拟商品如充值卡，与实物商品必须拆分，对账和履约逻辑完全不同）；
 - 活动独立要求（如部分活动商品需单独发货统计，按活动规则拆分）。
