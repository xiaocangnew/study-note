### 学习机的领域拆分问题(关注拆分依据)
1. 我们基于ddd领域驱动设计思想， 将学习机的业务拆分框架 拆分为「核心域、支撑域、通用域」三大类，
   1.1. 核心域：1. 练习评估域(练习创建 / 批改 / 结果分析)。 2. 知识图谱域(跟踪知识点掌握度)。3. 学习路径域（个性化学习推荐 如按薄弱点推课程）
   1.2. 支撑域：1. 课程资源域(教材版本，内容) 2. 作业域(作业管理)  3. 设备管控域(用户轨迹等)。 4. 用户域  5.拍照批改.  6. 活动激励域。
   1.3. 通用域：1. 消息触达.  2. 鉴权.  3.ai能力层
2. 为什么这么拆，核心依据是 “业务价值 + 用户闭环 + 技术可行性”
   2.1. 按 “业务价值优先级” 划分核心 / 支撑 / 通用域（战略层）
   学习机的核心目标是提升用户学习效果，因此我们优先将 “直接影响学习效果” 的域定为核心域：
   2.2. 按 “用户行为闭环” 划分域的职责边界（业务层）
   学习机的核心用户行为是「学→练→反馈→提升」，我们的域拆分严格对齐这个闭环，本质：每个域只做 “闭环中的一个环节, 避免 “跨域职责混乱” 的耦合过高
   2.3. 数据自治性（DDD “聚合根” 思想）
   每个服务管理自己的核心数据，避免跨服务查库：
   2.4. 按 “聚合根 + 康威定律” 划分限界上下文（战术层）
   1. 拆分到具体域内部时，我们用两个细节原则确保 “高内聚、低耦合”：
   2. 聚合根边界：比如「练习评估域」的核心聚合根是 “练习”，包含 “练习题目、练习结果、批改记录”（强关联，需原子操作），而 “课程列表” 属于「课程资源域」的聚合根，两者通过 “练习关联的课程 ID” 对接，不强行放在一个域；
   3. 康威定律：我们按 课程组、练习组、家长产品组” 划分团队，对应「课程资源域、练习评估域、家长管控域」—— 练习组改练习功能时，无需和课程组协调，迭代效率提升 50%。
3. 拆分后的效果
   3.1. 业务效果：核心目标（学习效果）显著提升
   ① 学习闭环完整性：拆分后，用户从 “看课程→做练习→看反馈→补弱” 的路径转化率提升 25%（之前因域耦合，练习入口隐藏在课程页，拆分后练习域独立，入口更清晰）；
   ② 个性化效果：核心域「学习路径域」独立后，投入资源做 AI 推荐算法，用户 “薄弱点课程的完课率” 从 40% 提升到 65%（之前推荐逻辑混在课程域，迭代慢）；
   ③ 家长满意度：「家长管控域」独立后，家长布置作业的操作步骤从 5 步减到 3 步，家长端 “作业布置成功率” 提升 30%，投诉量下降 40%。
   3.2. 技术效果：迭代效率 + 系统稳定性双提升
   ① 迭代速度：核心域需求响应周期从 2 周缩短到 1 周（比如练习域要加 “错题重练” 功能，无需依赖课程域，独立开发即可）；
   ② 故障隔离：去年练习域因题库接口 bug 导致练习无法生成，仅影响 “练习模块”，课程播放、家长管控等功能正常，故障影响范围缩小 70%（之前未拆分时，一个 bug 可能导致整个 APP 崩溃）；
   ③ 资源复用：通用域「缓存服务域」复用后，课程列表查询响应时间从 500ms 降到 100ms，服务器资源占用减少 30%。



### 学习机碰到的问题(练习记录中题目结果字段太大 1k到200k之间)
1. 主要问题：存储效率降低
    1. 行溢出导致的碎片化：InnoDB 对单行数据有长度限制（约 8KB，超过则触发 “行溢出”）。大字段（如 200k 的 TEXT）会被拆分到独立的 “溢出页”，而行所在的主数据页仅保留指向溢出页的指针。
       结果：一条记录可能分散在多个物理页中，读取时需要多次 IO，且页与页之间可能物理地址不连续。
    2. 频繁更新 / 删除导致的碎片化：更新大字段时，若新值长度超过原空间，会导致记录被移动到新页，原页留下 “空洞”（未使用的空间）。
       删除包含大字段的记录时，原页空间难以被新记录复用（因新记录可能 smaller），积累大量碎片空间
       磁盘空间浪费：
       碎片空间无法被有效利用，表占用空间可能比实际数据量大几倍。
       IO 性能下降：读取数据时需要扫描更多不连续的页，增加随机 IO 次数（导致查询性能降低）。

2. 解决方式：
   2.1. 通过innodb_page_size设置更大的页（如 32KB、64KB），减少大字段导致的行溢出（需在初始化数据库时配置，无法动态修改）。
   2.2. 重建表优化物理存储,可以清理碎片。 ALTER TABLE 表名 。 这个支持在线ddl。
   2.3. 将大字段进行独立存储，压缩存储。
