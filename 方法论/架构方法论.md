### 领域驱动设计，数据驱动开发(数据思维)
1. 数据驱动开发 (根据数据指标，决定下一步开发要提升哪些数据指标，包括业务向的数据指标，新能向的业务指标)
2. 数据驱动设计 (根据当前的数据指标，决定把设计重心放到那块，比如流量很小，就不需要设计很复杂。 流量很大，设计时就需要考虑qps，缓存等。 用户访问很少，就不需要过度设计，只要满足功能即可)


### 架构设计中的原则依据
1. 关注点分离是指导系统整体结构拆分的宏观原则，
             将系统分解为相互独立的部分，每个部分聚焦于一个清晰的功能或职责范围。目标是降低复杂度，让每个部分可独立设计、开发和维护。
              1.1. 单一关注点 (每个模块 / 组件只负责一个明确的任务，不混合无关逻辑)
              1.2. 关注点隔离 (不同关注点之间通过明确的接口交互，内部实现细节隐藏)
              1.3. 多维度拆分 (功能维度：按业务功能拆分; 技术维度：按技术职责拆分如日志、安全、缓存; 横切维度：跨越多个功能的通用关注点; 层次维度：按抽象层次拆分MVC)
2. SOLID是面向对象设计中确保代码质量的微观准则
              单一职责(避免大类), 开闭原则(对扩展开放，对修改关闭),  里氏替换原则, 接口隔离原则(避免万能接口), 依赖倒置原则(高层模块不依赖低层模块，两者都依赖抽象；抽象不依赖细节，细节依赖抽象)

### p7核心设计思维是 “分层解耦”(是解决 “系统复杂度” 的通用方法论)
1. 核心原因是：几乎所有系统的演进痛点（扩展性差、故障扩散、迭代效率低），本质都是 “模块耦合过紧” 导致的。
2. P7的关键能力: “根据需求复杂度动态调整分层粒度，判断是否需要解耦、解耦到什么程度”
3. 明确 “分层解耦” 的本质：不是 “拆分”，而是 “问题隔离”
          很多人误以为 “分层解耦” 就是把系统拆成 “接入层、业务层、数据层” 等固定模块，这是对方法论的误解。
          P7 视角下，分层解耦的核心目标是：将 “不同维度的问题” 隔离在不同模块中，让每个模块只解决 “单一类型的痛点”，避免一个模块的改动牵连整个系统。
4. 需要使用这个分层接偶思维的系统：
         4.1. 复杂业务系统：多角色、多流程、多规则（如电商、金融、教育）
                   核心痛点： “业务逻辑交叉耦合”，分层解耦能避免 “改一个功能，崩一片模块”。
         4.2.  技术基础设施：支撑多业务、高可用（如中间件、存储架构、监控系统
                   核心痛点： “技术能力与业务需求强绑定”，分层解耦能让技术能力 “复用”，避免为每个业务重复造轮子。
                   分层解耦方案：抽象层 -> 实现层 --> 业务适配层
         4.3.  长期演进需求：数据量 / 并发量会持续增长（如用户从 10 万到 1000 万）

### 业务拆分方式
> 业务复杂度：业务逻辑复杂（如金融）优先用 DDD / 六边形架构；业务简单（如工具类）优先用功能模块 / FaaS。
技术诉求：高并发读优先用 CQRS；异步解耦优先用 EDA；跨系统整合优先用 SOA。
组织规模：小团队（10 人内）优先按功能模块拆分（减少协作成本）；大团队优先按业务能力 / 团队结构拆分（符合康威定律）。
合规要求：强合规领域（如支付、医疗）必须按合规边界拆分敏感服务。
1. ddd
2. 功能模块
   按 “业务功能”（用户能感知的操作）划分模块，比如 “订单模块” 对应的是 “下单、查订单、取消订单” 这些用户能理解的业务功能。
   但拆分时只关心 “这些业务功能的技术实现要放在一起”，
   不深入思考业务背后的规则边界。 比如用户下单操作时，会把支付/库存校验扣减 相关代码都放到订单逻辑里。
3. 流量/资源
   高并发服务单独出来。
4. 数据边界
   适用于 数据密集型业务（如 CRM、供应链）、对数据一致性要求高的场景。
5. 角色/终端
   核心思路：因为不同角色 / 终端的需求、流量特征、权限逻辑差异极大，拆分后可独立迭代、针对性优化，
   政务系统：市民服务端（高频简单操作）、工作人员端（复杂审批流程）、管理端（数据监控、权限配置）。
6. 团队划分
7. 业务能力：
   以 “企业能为用户提供的价值能力” 为单位拆分，而非单纯的 “功能集合”。
   区别于 “功能模块”（如 “用户管理”“订单管理” 是 “做什么”），“业务能力” 更宏观（如 “客户获取能力”“订单履约能力” 是 “能提供什么价值”）

### 可以使用的架构方式(（“拆完后如何组织交互”）)
2.3.0. 单体架构优化
描述：即使不转向微服务，也可以通过对现有的单体应用进行模块化、分层等优化来提升其性能和可维护性。
适用场景：对于规模较小的应用或者那些不需要频繁变更和扩展的应用来说，优化单体架构可能是一个更简单且成本效益更高的选择。
2.3.1. 微服务架构(整个系统的 “服务集群组织”)
适用场景: 当应用需要高度扩展性和灵活性时使用，特别是对于云原生应用来说非常合适。
优点: 每个服务都可以独立地进行开发、部署和扩展；提高了故障隔离能力。
缺点: 增加了分布式系统的复杂性，如服务发现、负载均衡等问题。
2.3.2. 面向服务的架构（SOA）
描述：SOA是一种将应用程序的不同功能单元（称为服务）通过定义良好的接口和协议联系起来的设计方法。这些服务是独立的，并且可以通过网络进行通信。
适用场景：适合于需要集成多个现有系统的大型企业环境，尤其是那些希望重用已有组件或服务的企业，实现服务的重用和整合。
核心思想: 核心在于通过网络将不同的功能模块（服务）连接起来，这些服务使用通用协议进行通信
关注点:  如何定义服务接口以及如何使这些服务之间进行有效的交互。它强调的是服务的可发现性、互操作性和松耦合特性。
例子: 银行系统中，不同银行服务如贷款、存款、信用卡等可以作为独立的服务来开发和维护。(ddd在这里面也组合使用，模块内提效)
2.3.3. 事件驱动架构（EDA）
适用场景：非常适合需要处理大量并发请求、对实时数据流处理有要求的应用，或者需要响应外部事件的应用。
优点: 提高了系统的可扩展性和可伸缩性；非常适合异步处理。
缺点: 设计和调试较为复杂；可能难以追踪事件流程。
例子: 在线广告/新闻系统根据用户的点击行为实时调整投放策略。
2.3.4. 六边形架构（单个服务 / 模块的 “内部结构”）
描述：简称“洋葱架构”。又称端口和适配器架构。 以 “领域模型”（业务核心）为中心，外层通过 “适配器”（Adapter）对接外部依赖（如数据库、API、消息队列）
设计理念： 核心逻辑隔离化。 “隔离业务逻辑与外部技术实现”，聚焦业务逻辑的独立性和可测试性。
适用场景：业务逻辑复杂且需长期迭代的系统（如金融核心系统）、需适配多外部依赖的场景（如同时支持 MySQL 和 MongoDB 存储）。
2.3.5. 函数式编程和架构(FP)
描述：强调使用纯函数、避免共享状态和副作用的原则，减少了并发编程中的复杂性。有助于构建更加稳定和可预测的系统。
适用场景：特别适合于并发处理、大数据分析以及任何需要高度可靠性和一致性的场景，计算密集型。
2.3.6 微内核架构
描述: 微内核架构也被称为插件架构，它将最小化的基础框架与扩展功能分离。核心系统提供基本的服务，而额外的功能则通过插件或扩展实现。
设计理念：核心功能最小化。适合需高度稳定且功能频繁迭代的系统。
示例: 操作系统设计（如Windows NT）、IDE（集成开发环境）允许用户安装各种插件来增强功能。

### 微服务与soa架构的联系：
1. 两者都旨在通过分解大型应用程序为较小的部分来提高可维护性、可扩展性和复用性。
2. 都强调服务之间的松耦合，以及如何定义清晰的服务接口以便于交互。
   与soa的区别：
1. 规模和粒度：SOA：倾向于较大的、更粗粒度的服务，这些服务可能包含多个业务功能。它们通常用于企业级应用集成。微服务：强调细粒度的服务划分，每个服务专注于单一的业务能力。这种设计更适合于快速迭代和部署。
2. 通信机制：SOA：常用的企业服务总线（ESB）作为中介来处理服务间的通信，这可能会引入额外的复杂性和瓶颈。微服务：倾向于使用轻量级的协议如HTTP/REST或消息队列进行直接通信，减少中间件依赖。
3. 技术栈灵活性：SOA：由于其集中式管理特性，往往要求所有服务遵循相同的技术标准和协议。微服务：允许每个服务选择最适合自身需求的技术栈，提供了更大的灵活性。


### 项目架构设计常用的方法论和适用场景
1. ddd-领域驱动开发
      适用场景：业务复杂的系统/长期演进的系统 (复杂系统的最大风险是 “技术设计与业务脱节”)
      原因： DDD通过“领域建模” 让开发团队与业务专家深度协作，将模糊的业务需求转化为清晰的模型，确保系统设计 “贴合业务本质”，减少后期因业务理解偏差导致的重构成本。
2. tdd-测试驱动开发
      核心流程：“先写测试，再写实现”：在编写功能代码前，先定义测试用例（验证功能是否符合预期），然后编写最小化代码满足测试，最后重构优化代码。
      适用场景： 
           1. 高可靠性要求的系统：如医疗设备软件、航天控制系统、支付核心模块等，需严格避免逻辑错误。
           2. 频繁变更的代码：如工具类库、框架组件，需通过测试保障修改后不破坏原有功能
      原因：传统开发中，“先实现后测试” 容易导致测试被忽视（如赶进度时跳过测试），或测试覆盖不全。TDD 强制 “测试先行”，能更早暴露逻辑漏洞，且测试用例本身就是代码的 “验收标准”，同时倒逼开发者写出更模块化、低耦合的代码（便于测试）。
3. bdd-行为驱动开发
      核心思想：在 TDD 基础上，用自然语言（如中文、英文）描述系统行为（而非纯代码测试用例），让业务人员、测试人员、开发人员能共同理解和验证功能。
      适用场景：跨角色协作的项目：业务人员（不懂代码）需要参与需求验证的场景（如互联网产品、ToB 业务系统）。
4. fdd-特征驱动开发
       核心思想：
              以 “功能特征（Feature）” 为最小开发单元，将大需求拆分为可执行的小特征（如 “用户修改密码”“订单超时自动取消”），每个特征按 “规划→设计→构建” 的流程迭代开发。
       适用场景：
              需求明确且可拆分的项目：如电商平台的功能迭代（新增 “优惠券核销”“地址管理” 等独立特征）。
              中小型团队快速交付：特征粒度小，可并行开发，适合需要快速看到成果的场景。
5. mdd-模型驱动开发
   核心思想：
         通过可视化模型（如 UML、领域特定模型） 描述系统，再通过工具自动（或半自动）将模型转换为代码，减少手动编码工作量。核心是 “模型即代码”。
   适用场景：
         领域固定且模型稳定的系统：如电信行业的套餐配置系统、工业控制中的设备流程建模（领域规则固定，模型可复用）。
         重复开发场景：需要快速生成标准化代码（如 CRUD 接口、基础框架代码）的项目。
6. udd-用户驱动开发
7. ood-面向对象开发
8. cdd-契约驱动开发
   核心思想： 
         先定义服务间的契约（Contract）（如 API 接口的输入输出、格式、异常处理），再基于契约开发服务，确保服务调用方与提供方的一致性。
   适用场景：
         分布式系统或微服务架构：如多个微服务之间的调用（需明确接口规范）、前后端分离项目（前端与后端的 API 约定）。
         跨团队协作：不同团队开发的服务需要集成时（如第三方支付接口对接）。
9. ddd-数据驱动开发 
       核心思想：强调通过数据的采集、分析和反馈来指导软件设计、功能迭代和决策优化。它的核心逻辑是：“让数据决定系统应该做什么，而不是仅凭经验或直觉”。
       开发流程的核心：
              开发前：通过数据分析明确用户需求、业务痛点（而非依赖主观判断）；
              开发中：设计系统时优先考虑数据的采集、存储和分析能力；
             上线后：基于用户行为数据、业务指标数据持续优化功能，形成 “数据反馈→迭代改进” 的闭环。

**总结：方法选择的核心原则**
这些方法并非互斥，实际开发中常结合使用（如 “DDD+TDD” 构建复杂业务核心，“BDD+CDD” 保障微服务协作）。选择的关键是：
业务复杂度：复杂业务优先 DDD，简单业务可直接用 OOD；
团队构成：跨角色协作选 BDD，技术团队主导可选 TDD；
系统类型：分布式系统重视 CDD，用户端产品重视 UDD；
交付节奏：快速迭代可选 FDD，模型稳定可选 MDD。
最终目标是 “用合适的方法解决当前场景的核心问题”，而非教条式套用。

                       例子2: 内容平台需处理 “内容提交、AI 初审、人工复审、违规处理、合规归档”，各职能独立，AI 初审规则频繁迭代，人工复审流程稳定。
        4. 方法 4：流量 / 数据隔离法（适用于 “存在热点流量、海量数据” 的场景）
                      关键特征：存在明显流量分层（如 90% 流量是热点，10% 是普通）、数据量级差异大（如热门评论 100 万条，普通评论 10 条）。
                      边界规则：资源隔离规则，数据分片规则，优先级规则，降级规则
                       例子1: 评论中台需支撑 “下单主流程评论（低并发、强一致）” 和 “热点视频评论（高并发、弱一致）”，流量差异显著。边界规则：资源隔离：主流程评论领域用 TiDB 主集群（强一致），热点评论领域用独立 Redis 集群 + ES 集群（高并发）；数据不互通：热点评论不进入主流程数据库，避免拖慢主流程查询（如热门视频评论仅存 ES，不写入 TiDB）。
                       例子2: 短 URL 系统需处理 “短 URL 生成（低并发、写操作）” 和 “短 URL 跳转（高并发、读操作）”，读写流量差异大。 边界规则： 资源隔离：短URL生成领域用 HBase（持久化），短URL跳转领域用 Redis 集群（缓存最近 6 天数据，占 90% 读流量）；
        5. 核心产出： 输出：限界上下文划分、交互契约文档。
第三步：阶段2模型设计- 聚合与实体设计
        1. 核心实体识别，聚合根判断标准（是否承载核心业务逻辑、是否有唯一标识)
        2. 核心实体行为定义, 行为边界 checklist（是否属于实体核心职责、是否依赖其他实体）
        3. 域间交互设计
        4. 核心产出： 输出：聚合设计图、实体 / 值对象属性表。 实体行为清单、行为触发条件
第四步：阶段 3技术落地 - 服务抽象(核心动作：区分领域服务与应用服务，降低变更影响)
        1. 识别底层通用服务：
                1. 领域服务：处理领域内跨实体的业务逻辑。 应用服务：编排领域服务与外部服务。 
                将 “分单规则”“排期预占”“订单状态流转” 等通用逻辑抽象为领域服务，避免业务变更影响底层；
        2. 选择服务抽象方式：
                初期用 “被动抽象法”：当多个业务复用同一逻辑（如不同工厂的排期预占逻辑），再抽象为公共服务；
                成熟期用 “强制标准接口法”：底层服务仅提供标准接口（如订单创建接口仅接收排期 ID、商品信息），业务个性逻辑由上层服务实现（如不同品类的订单售后差异）；
        3. 禁止跨层级调用：同层级模块（如排期系统内的 “分单模块” 与 “预占模块”）不直接调用，需通过上层服务聚合，避免循环依赖。
        4. 核心产出：服务分层图、标准接口文档。
第五步：阶段 3技术落地 - 验证与落地
        1. 增量拆分：若原系统庞大，先从 “非核心流程” 试点（如先拆分排期模块，再拆分订单模块），避免一次性拆分风险；
        2. 验证维度：
                业务验证：走查核心流程，确认拆分后业务逻辑无遗漏（如排期创建→订单生成→物流发货全链路通畅）；
                性能验证：压测高频接口（如排期创建、订单查询），确认响应时间与吞吐量达标；
                变更验证：模拟业务变更（如修改分单规则），确认影响范围仅局限于排期上下文；
        3. 持续迭代：定期回顾拆分效果，若业务变化导致领域边界模糊（如新增 “排期变更触发订单修改” 需求），及时调整上下文与聚合设计。
        4. 核心输出：试点拆分计划、验证报告、迭代优化方案。


### 限界上下文 vs 聚合根
限界上下文：
     是业务语义的边界。每个限界上下文有自己独立的领域模型、术语和上下文环境。它通常对应一个子系统或业务能力模块。
聚合根：
     是领域模型中的一个实体，作为一组相关对象（聚合）的根节点，负责维护聚合内部的一致性和业务规则。
聚合根的数量是灵活的
   每个限界上下文内部可以包含：
        0个聚合根（极少见，比如纯值对象或查询场景）
        1个聚合根（简单场景）
        多个聚合根（常见，复杂业务逻辑）


### 事件风暴聚类法- 电商退款系统
> 业务背景 电商退款涉及 “用户申请→客服审核→财务退款→库存回滚→优惠券恢复”，多角色（用户、客服、财务）参与，流程交叉。
领域确定与边界识别步骤
1. 梳理领域事件（事件风暴核心步骤）：
      召集产品、研发、运营，用贴纸标注事件（黄色）、命令（蓝色）、角色（绿色）：
          事件：退款申请提交、退款审核通过、退款审核拒绝、财务退款成功、库存回滚成功、优惠券恢复成功；
          命令：用户提交退款申请、客服审核退款、财务发起打款；
          角色：用户、客服、财务、库存系统、优惠券系统。
2. 事件聚类（确定领域）：
      按 “事件的核心关联方” 聚类：
          聚类 1：退款申请与审核（事件：退款申请提交、审核通过 / 拒绝；角色：用户、客服）→ 退款审核领域；
          聚类 2：退款打款（事件：财务退款成功；角色：财务、支付系统）→ 退款打款领域；
          聚类 3：关联资源回滚（事件：库存回滚成功、优惠券恢复成功；角色：库存系统、优惠券系统）→ 退款资源回滚领域。
3. 定义边界规则：
         事件驱动：退款审核领域审核通过后，发布 “退款审核通过事件”，退款打款领域和退款资源回滚领域订阅该事件（不直接调用）；
         无跨领域数据依赖：退款打款领域仅接收 “退款单 ID + 金额”，不查询退款申请原因（由退款审核领域单独存储）。

### 事件风暴聚类法- 网约车派单系统
> 业务背景: 网约车涉及 “乘客发单→平台匹配司机→司机接单→行程跟踪→费用结算”，多角色（乘客、司机、平台），流程交叉（如司机拒单需重新匹配）。
领域确定与边界识别
1. 梳理领域事件：
        事件：乘客发单、平台匹配司机、司机接单、司机拒单、行程开始、行程结束、费用结算完成；
        命令：乘客提交订单、平台发起匹配、司机确认接单、平台发起结算；
        角色：乘客、司机、平台调度系统、结算系统。
2. 事件聚类：(按 “事件的核心关联方” 聚类：)
        聚类 1：订单与匹配（事件：乘客发单、平台匹配司机、司机接单 / 拒单）→ 订单匹配领域；
        聚类 2：行程跟踪（事件：行程开始、行程结束）→ 行程跟踪领域；
        聚类 3：费用结算（事件：费用结算完成）→ 费用结算领域。
3. 边界规则：
        订单匹配领域发布 “司机接单事件”，行程跟踪领域订阅后开始跟踪（不直接调用）；
        费用结算领域仅接收 “行程 ID + 里程 + 时间”，不参与匹配逻辑。

### 核心子域是如何确定的。
1. 列出所有用户价值点，
2. 分析价值的独特性和壁垒，  
   1. 内容（教材、题库）：可以被竞争对手复制、购买。是必要但不充分的条件
   2. 批改：尤其是客观题批改，技术壁垒不高。主观题批改有壁垒，但最终会趋于同质化，成为一种“优质基础设施”。
   3. 知识图谱可视化：技术上有一定难度，但本质上是一种“报表”。它告诉你“你哪里弱”，但无法告诉你“接下来怎么做”。
   4. 个性化学习路径：这是将内容、批改、学情分析三者融合起来，做出智能决策的能力。它直接回答了用户最根本的问题：“我接下来该做什么？” 这个能力的背后是复杂的算法、教研模型和数据积累，构成了很高的技术和数据壁垒。
3. 识别业务的“飞轮效应”起点
    1. 一个好的个性化推荐系统，会让学生更有效地提升成绩。
    2. 成绩提升带来的正反馈，会让学生更频繁地使用产品，产生更多数据。
    3. 更多的数据会让推荐系统更加精准。
    4. 这个不断自我强化的循环，其启动器和加速器，就是“个性化学习路径”能力。


### ddd领域驱动设计中，核心域会变化吗
> 公司在不同发展阶段，核心领域的定义和优先级会动态变化。这正是 DDD 领域划分的灵活性所在。
> 核心领域的本质是 “当前阶段最需要投入资源解决的关键问题”，当业务目标和核心矛盾变化时，核心领域的优先级自然会随之调整。 它看 “资源投入的‘深度’与‘战略价值’”，而非 “迭代的‘频率’与‘数量’”
> 两个维度拆解：维度1：迭代的 “资源投入强度”，远重于 “迭代次数”; 维度 2：迭代的 “价值指向”，是否匹配 “核心矛盾”
> 一定是完成核心业务闭环中的环节

比如电商的不同阶段：
1. 冷启动期：核心矛盾是 “从 0 到 1 建立业务闭环”，核心领域向 “基础交易能力” 倾斜
2. 成长期：核心矛盾是 “从 1 到 N 扩大规模”，核心领域向 “用户增长 + 交易效率” 倾斜
3. 成熟期：核心矛盾是 “从规模到利润，提升精细化运营能力”，核心领域向 “效率 + 体验” 倾斜
4. 转型期：核心矛盾是 “突破增长瓶颈，寻找第二曲线”，核心领域向 “新业务模块” 倾斜

学习机的不同阶段：
1. 冷启动期：内容质量与家长信任是核心，需快速验证价值。 要回答的核心问题： “用户为什么要用我这个新产品？”
2. 扩张期：内容广度与个性化推荐是关键，需覆盖全学段并精准匹配需求。要回答的核心问题： “用户为什么持续相信我？
3. 粘性期：AI 深度体验与学习效果追踪是重点，需通过技术增强依赖。要回答的核心问题： “用户为什么离不开我？”
4. 商业化期：订阅服务与 B 端拓展是突破点，需从硬件转向服务生态。要回答的核心问题： “如何构建生态和网络效应？”
5. 成熟期：数据驱动与品牌壁垒是护城河，需持续优化内容与技术。

### 随着产品处于不同时期，核心域不断变化，该怎么迭代
> 如果每次业务重心变化，我们都要对服务进行大刀阔斧的拆解和合并，那带来的成本和不稳定性将是灾难性的。
服务不应该，也不需要“不断地”进行拆分合并。 正确的演化策略是 “小步快跑，持续重构，并优先通过改变服务内部结构来适应变化”。
1. 核心域变化，但边界清晰
          清晰的限界上下文边界，就像国家的疆界。国力（核心域）的兴衰更替，并不需要频繁地重新划分国界。
2. 原有上下文内出现新的、重要的子场景
           1. 演化策略：优先内部模块化，而非立即拆分
           2. 评估拆分必要性
                  变化频率不同（例如，模拟考试的规则总在变，而课后练习很稳定）。
                  资源需求不同（例如，口语练习需要大量GPU资源，而课后练习是CPU密集型）。
                  团队规模扩大，不同团队负责不同子场景，共享一个服务导致部署冲突。
              当这些摩擦成本大于拆分和运维的成本时，才进行拆分。
3. 出现跨上下文的复杂业务流程
           1. 演化策略：引入编排层，避免创建“上帝服务”
                       情况描述： 新增一个“假期训练营”活动，它需要从学习路径服务获取计划，从内容服务拉取题目，在练习服务中完成，并在用户服务中积分。
                       解决方案： 创建一个新的上下文 及其对应的训练营服务。 这个新服务的职责不是直接实现业务逻辑，而是编排其他上下文的服务。 它通过调用其他上下文的应用服务（而非直接操作其数据库）来完成整个流程。
4. 服务演化的基本原则
          1. 边界第一，拆分第二： 首要任务是定义清晰的限界上下文边界。一个设计良好的边界具有极强的生命力，可以容纳内部业务的很多变化。
          2. 忍受初期的“不完美”： 不要追求一步到位的“完美架构”。允许一个限界上下文在初期作为一个稍大的服务存在，只要其内部模块化良好。
          3. 让“疼痛”指导拆分： 当你在一个服务内部感受到了明显的摩擦时（如团队协作困难、部署频繁冲突、技术栈不匹配、性能难以隔离），这才是考虑拆分的信号，而不是因为“理论上它应该独立”。 
          4. 合并要极其谨慎： 服务的合并通常是架构上的一种“退步”，通常只在前期拆分错误，导致服务间耦合严重、调用链路复杂到无法维护时才会考虑。
          5. 投资于防腐层和标准化通信： 无论服务如何演化，在上下文之间使用明确定义的API、领域事件进行通信，并坚持使用防腐层（Anticorruption Layer）来隔离变化，这是架构能够灵活演进的基石。



### APP的首页单独起一个服务，是单独的上下文吗？
1. “入口聚合微服务” 即使作为独立微服务存在，也不构成单独的限界上下文，也无需归属到任何业务上下文。
       它的价值是作为 **“业务上下文的‘前端协调器’”**，通过聚合和适配简化前端调用，同时隔离业务上下文与前端的直接交互，是一个业务网关。
       调用链路： user -> nginx网关(处理ssl解密，静态资源等,4层网络协议网关) -> 微服务网关(ab实验，限流，鉴权等，7层网络协议网关) -> 业务网关(特定场景聚合，不是服务聚合)/微服务 -> 微服务
2. 区分入口聚合微服务和 app首页能力。 如果app首页需要运营人员配置，给不同人群展示不同页面，或者配置运营活动位。那么这个首页就有了业务属性。 就能单独成一个上下文了


### 如何用 DDD 实现业务闭环设计？(流程控制必然是业务闭环的)
1. 第一步：用 “限界上下文（BC）” 定义闭环的 “业务边界”，明确 BC 的 “输入” 和 “输出”
2. 第二步：用 “聚合根（AR）” 作为闭环的 “状态载体”，聚合根必须包含 “完整的状态机”
3. 第三步：用 “领域事件 + 事件驱动” 串联闭环的 “流程节点”。每个关键状态变更都发布 “领域事件”
4. 第四步：用 “领域服务 + 政策” 处理闭环中的 “复杂协同”
5. 第五步：用 “终态设计 + 异常补偿” 确保闭环 “必有结果”。定义明确的 “终态”：每个流程必须有 “成功终态”，设计 “超时 / 异常补偿”

### 重构问题描述：
1. 维护成本高，开发迭代效率低(服务语言框架不统一、框架老旧;数据链路不统一，同一种功能多种实现; 测试环境搭建困难，联调效率低; 配置分散)
2. 数据不一致问题 (取值逻辑不一致, 下游依赖数据获取链路不一致)
3. 稳定性低 (服务框架老旧，本身没有 tp99 和 slo 监控; 服务可观测性差，定位问题困难; 框架老旧，性能差，稳定性保障机制不完善)
4. 工程质量差 (单测覆盖率低于10%，无接口测试; 代码规范问题 x 个，研发指标得分73.69)

### 领域建模的认知增加：
0. 核心领域是建模中最关键的一步。 (反映了业务中核心关注点，聚焦业务价值，指导架构决策，围绕它来设计软件架构。 优化资源配置，将研发中心放到核心上。对非核心功能采用更加经济高效的实现方式。不仅帮助团队集中精力解决最关键的业务问题，还为后续的设计和开发工作提供了清晰的方向)
   有时团队可能会陷入实现细节中，而忽视了对核心领域逻辑的理解和建模。
   如何识别核心领域？ 基于用户使用场景频率， 用户需求与业务目标之间的交集。 比如x1学习机。业务目标是释放家长，让孩子自主学习。
   当前用户学习与练习场景占到总使用的80%. 所以是核心领域。用户的薄弱点与知识图谱分析， ai类使用， 目的都是为了让孩子更精准的定位自己的问题/解决学习问题， 虽然他们很重要，但更偏向工具类。

1. 作业在发布时就会生成练习记录。
   认知误区： 认为作业就是一次练习， 一次练习有练习记录，所以作业也会有练习记录， 在布置时就会生成记录。(但作业和练习记录是两个领域)
   领域知识：
   作业是一个单独的领域(核心关注点： 布置作业流程的各个环节痛点(选择内容，发布作业，进度监控，作业批改，作业反馈)，作业状态机，各种触达， 用户作业功能使用率， 作业布置后完成率，作业最佳布置长度分析等)，
   练习记录是一个单独的领域(核心关注点：练习内容，练习方式，练习结果)
   作业与练习领域分离后的好处：
   区分后可以独立演化，降低领域开发理解成本。比如字词听写新增机上练习模式后，不需要作业也增加新练习模式，练习模式本质上是练习记录的参数。
   隔离失败风险，作业的发布不需要依赖练习记录服务的存活，提升核心服务的可用性。

2. ai对话领域拆分。
   认知模糊区域： ai对话包含场景-对话-轮次。  
   练习结果进行ai诊断的产品需求是否能套用ai对话的能力。产品需求里ai诊断是一次性行为，中间调用ai还可能失败，需要进行重试。
   a. 如果能套用，则需要融合进ai对话的能力模型里。 需要对ai对话的轮次进行 1:n的关系套用(比如调用ai诊断接口成功，但是进行ai对话时失败了，重试对话)。
   那么就需要在ai对话能力模型里新增一层聚合层。
   b. 如果不套用ai对话模型， 那么仅仅是把ai当成一个rpc，获取ai的结果，而不是一次对话。
   基于a和b方案，更倾向于b方案， 那么就对原有的ai对话模型进行领域扩充， 对话是ai的一个领域， rpc工具调用也会是ai的一个领域。 ai有两个子领域。

3. 实体关系：
   实体关系是领域模型的具体体现 (实体关系不仅包括数据库表， 还包括redis 数据结构， config的结构，enum枚举等)
   在数据库这个case中，就必须按照领域的方式来严格实现， 每次新增表都要思考是否在领域范围内， 表上新增字段也是一样

4. 领域模型：
   要跳出现有代码的逻辑， 在业务上思考， 什么是通用流程， 正确的模型是什么。 然后再看代码， 看看gap 在哪里，怎么补齐。
