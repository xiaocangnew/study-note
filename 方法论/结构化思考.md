### 做事情的方法论 (指做事的原则， 基础思考方式).
>>> 8年工作经验， 在面试中，总是被问到方法论。
0. 在有很多问题需要排队解决时，根据做事四象限， 最紧急的事情是什么，最重要的事情是什么。
    1. 什么是紧急，
    2. 什么是重要，考虑投入产出比(比如一个需求，收益不是很大，那么就不需要使用很复杂和完善的技术进行实现，怎么简单怎么来)
1. 在解决单个问题时： 比如5w1h 方式
    1. WHAT定任务 (任务是什么，目标和要求是什么， 预期成果是什么)
    2. WHY明意义 (为什么要做， 这项任务与战略有什么关联， 这项任务的意义和价值是什么)
    3. WHERE 辨路径 (应用场景是什么。 有什么特征，核心约束)
    4. WHO配资源 (谁负责， 需要谁来配合协调， 如何统筹安排各方资源)
    5. WHEN定时间 (如何安排任务进度，各个阶段时间明确， 是否有buffer， 事前，事中，事后怎么做)
    6. HOW定计划执行 (对要经历哪些阶段， 影响任务达成的因素有哪些，最有效的方法是什么。任务关键环节的把关是否到位, 是否有全流程的追踪)
2. 在描述自己碰到最大的挑战时，用STAR法则(situation, task, action, result)
3. 在做系统设计时，有哪些基本原则，微服务拆分的基本原则。 项目设计的几种方式： ddd, tdd, udd等

### p7级别的思考方式
> 思考框架的核心价值是 “高效解决复杂问题、避免决策偏差”
1. 5W1H 用于 “明确边界、理清全貌”（如需求定义、项目启动、跨团队协作对齐、模糊问题澄清）
2. 5Why 用于 “穿透表象、定位根因”（如故障排查、问题复盘）
3. RICE：需求 / 任务优先级排序（量化决策，reach影响范围+impact影响程度+confidence置信度+effort投入成本）
4. SWOT：方案 / 技术选型决策（全面评估利弊， strength优势 + weakness劣势 + opportunity机会 + threats威胁）
5. MECE：需求分析/架构设计等 (拆解问题时不重复=相互对立、不遗漏=完全穷尽 )
       5.0. 判断标准： 1. 可以解决当前问题。 2.拆解后所有子项能分配到具体任务 / 方案，无 “无法落地的空白区域”。
       5.1. 分层架构是 “按物理 / 功能层级” 的固定拆解模式，而 MECE 是 “通用的拆解原则”，可适配任何场景（包括但不限于架构分层）
       5.2. p7如何落地mece呢？
                5.2.1. 步骤1: 明确 “母项”—— 先锁定要拆解的核心问题 / 目标，必须具体可执行。     “优化 AI Agent”（太宽泛，拆解会混乱）“优化 AI Agent 复杂环境下的自主执行成功率（从 55% 提升至 90%）”（目标清晰，拆解有聚焦点）。
                5.2.2. 步骤2: 选择 “拆解维度”—— 按场景选合适的拆分角度
                              1. 架构设计、模块优化  ----> 按 “数据”，“算法”，“资源cpu/内存”，“网络”， “功能/模块” 纬度
                              2. 需求拆分、问题排查  ----> 按 “场景/对象”， “任务流程/用户旅程”，“任务类型” 纬度
                              3. 项目规划、流程优化  ----->按 “时间/阶段”，“投入/产出”， “角色/团队” 纬度
                              4. 故障排查、效果归因  ----->按 “问题类型” 纬度
                              5. 稳定性建设：
                                    (MECE拆分1-系统生命周期)产品需求、代码开发、运维部署、故障管理等系统全生命周期进行全方位去考量和设计。 
                                    (MECE拆分2-时间线*责任域) 按 “事前 / 事中 / 事后 × 业务 / 技术 / 数据” 拆分
                                    (MECE拆分3- 故障生命周期) 按事前 / 事中 / 事后 三个维度
                                    (MECE拆分4- 风险来源) 按内部系统、外部依赖、流量波动、人为操作
                                    (MECE拆分5- 技术层级) 按照 “基础设施→中间件→应用服务→业务逻辑”
                                    (MECE拆分6- 保障手段维度) 形成 “预防→监控→容错→恢复→优化” 的闭环
                5.2.3. 步骤3: 校验 “MECE”—— 可以用多维度交叉尝试去覆盖，保证无遗漏死角
6. 鱼骨法： (bug定位用)复杂问题归因。核心目标是从 “表层问题” 出发，层层挖掘 “潜在影响因素”，最终定位 “根本原因”。
           其结构像鱼骨：“鱼头” 是待分析的问题，“主骨” 是核心影响维度（如人、机、料、法、环），“子骨” 是各维度下的具体因素。
      6.1. 人(开发逻辑漏洞、测试场景覆盖不全)
      6.2. 机(服务器资源不足、接口性能差)
      6.3. 料(用户数据缺失、接口数据错误)
      6.4. 法(决策算法不合理、执行流程有缺陷)
      6.5. 环(环境问题，比如波动等)



### 对于解决问题，p7级别要有闭环思考的方法论
> 从 “被动解决问题” 升级为 “主动掌控问题全生命周期”—— 不仅要解决单点问题，更要确保问题的 “定义 - 方案 - 验证 - 迭代 - 沉淀” 形成完整链路，避免 “头痛医头” 或 “解决一个问题引发三个新问题”。
> 思考闭环不是 “一次性完成”，而是 “螺旋上升的全链路管理”。可以拆解为两个问题： 系统性思维 + 落地执行力：
> 避免 “局部闭环”：不能只关注技术环节，需拉通产品、测试、业务团队，确保 “问题定义与业务目标一致”。
具体步骤为：
1. 问题定义闭环(用 “问题拆解框架” 确保定义闭环： 针对表象使用5why连续追问法 + 量化问题指标)
2. 方案设计闭环(用 “方案分层设计” 确保落地闭环， 兼顾 “短期解决 + 长期扩展”。 兼顾 “技术可行性 + 业务价值 + 风险预判”； 提供多个方案，多维度对比)
3. 执行验证闭环(确保 “方案落地效果可量化、可回溯”： 定义明确的评估指标； 分层验证(测试->灰度->全量)，)
4. 迭代优化闭环(基于反馈持续调整，避免 “一劳永逸”： 持续跟踪线上数据，分析新场景)
5. 知识沉淀闭环(输出技术文档， 沉淀设计范式， 甚至推动工具化)


### 做一个需求时，p7级别的思考方式
> 风险先行,考虑全链路上有哪些卡点， 在执行落地分配时，考虑到哪些地方可能存在问题(人员，依赖，数据，时间等)
> 需求拆解(核心场景，核心约束，挑战在哪里)→架构分层→技术选型→关键设计(风险管控，优化策略)→监控告警->落地和演进” 全链路。

### p7架构落地能力--体系化拆解：业务层，技术层，团队层
1. p7拆解业务层，
       1.1. 按业务场景区分： “对齐业务目标→拆分业务模块→子场景细分→业务模块核心目标→明确技术支撑点”
       1.2. 按“用户旅程” 拆分(更贴合 C 端体验)。 每个环节对应 “业务目标 + 技术支撑”，优点是能直接对齐用户体验指标（如 “等待履约时长≤3 分钟”）。
       1.3. 按“组织架构” 拆分（更贴合跨团队协作）.每个部门对应 “业务模块 + 技术责任”，优点是责任边界清晰，避免跨部门推诿。
2. p7拆解技术层
       2.1. “基础层→能力层→治理层”
3. p7拆解数据层
       3.1. 数据流转视角，
       3.2. 数据生命周期
4. 团队能力层拆解：以 “角色 - 技能 - 工具” 为核心，支撑技术演进落地


### (所有项目-大模型)在生产环境中的要求： 稳定，安全，高效，可控，可维护，可迭代
1. 稳定(大模型负载均衡，降级， agent与workflow的稳定性控制)
2. 安全(不违规，敏感信息泄漏，幻觉，边界控制)
3. 高效(延时，内存占用，成本控制)
4. 可控(可观测：日志，打点，链路追踪，报警)
5. 可维护(工程化落地：配置中心-分环境隔离-测试-版本控制-部署)
6. 可迭代(如何进行迭代，确立迭代规则)

### 创建数据表时，就要想到
1. 数据从哪里来，有多少输入口(单条/批量， 数据的增长存储规模有多大，qps多高)
2. 数据要去哪里，都有多少调用方(查询耗时高低，查询频率)
3. 数据有几种更新方式，删除场景
4. 数据的生命周期(冷热数据存储)，
5. 状态机怎么流转 (考虑触发事件，异常处理，一致性保障)


### 使用mq时，就要想到
1. 数据的可靠性(丢失，重复消费)
2. 消息的顺序性(序列号)
3. 数据最终一致性( saga分布式事务 + 每日对比任务核对)
4. 消费失败处理(重复消费3次，失败进入死信队列，报警，)
5. 怎么监控(消费延时，队列堆积，报警)


### 使用redis时，就要想到
1. redis 资源模型(高cpu计算型，高占用内存型，高网络带宽型  ---> 大key等导致内存碎片，过期时抖动，网络占用)
2. redis常见的问题(与mysql数据一致性问题，持久化安全问题，高并发问题-缓存穿透雪崩等)

### 多角色/多状态/多平台
1. 登陆，未登陆，
2. 客户，商家，admin
3. h5，小程序，app，平板。

### 数据指标有哪些：
> 进行数据驱动时，前提是： 可量化(将业务指标转为数据指标， 数据可进行采集， 数据对比基准是明确), 
1. 业务价值指标(转化率，效率，质量，成本)
2. 用户体验指标(过程类指标，结果类指标)
3. 技术指标(性能指标，稳定性，资源占用率)
4. 风险与安全、合规指标(反爬虫，风控等)


### 推拉模型
1. 主动推送时，数据量小，优先保障核心场景， 延时低
2. 定时拉取时，数据量大， 设立版本号机制减少拉取数量， 延时高


### 系统如何演进
> 演进路线的核心是 “以业务价值为核心，用数据验证方向，靠研发保障落地，用合规守住底线”。
> 系统演进的最终目标都是 “规模(平台化生态化) × 效率(自动化、智能化)” 
具体步骤：
1. 锚定 “业务价值北极星”。（优先级最高）。
          1.1. 演进的本质是 “让功能 / 系统更有价值”，所以先明确：这个功能的核心目标是什么
          1.2. 业务系统： 锚定业务价值：和产品 / 运营深聊 3 个关键问题：用户核心痛点，业务目标， 商业 / 教育价值
          1.3. 基础系统： 锚定间接价值闭环：业务支撑率，稳定性，研发效率，成本控制
2. 用 “数据信号” 验证需求紧迫性（客观依据）。
      流量 / 使用数据：不是 “流量涨了就扩容”，而是看 “核心场景的压力点”：
          2.1. 高频场景：哪些功能使用占比超 60%
          2.2. 瓶颈信号：是否出现响应延迟（如拍照批改耗时超 3 秒）、报错率上升（如 OCR 识别失败率超 2%）、服务器负载过高（如峰值 CPU 使用率超 80%）？
          2.3. 用户反馈数据：投诉 / 建议中重复出现的问题？
3.  结合 “研发可行性” 确定落地节奏（现实约束）
          3.1. 研发侧需提供2类输入: 技术现状; 资源与风险：研发人力配比、技术债情况、新功能的 POC 验证结果
          3.2. 决策原则：“先解决‘能用’，再追求‘好用’”，避免 “技术超前但s落地不了”。
4. 业务系统的迭代：
          4.1. 通用系统迭代
                   1. mvp 最小验证；  2. 完善功能、提升用户体验与公司效率.   3. 平台化扩展(场景扩展和生态)
          4.3. 互联网电商：(以流量为核心，通过社交裂变、内容创新与全域协同实现用户增长，最终构建智能生态)
                   1. mvp(社交裂变=流量杠杆+轻量化供应链)；  2. 内容驱动阶段（体验优化）  3. 全域协同阶段（规模化扩张，公私域流量整合，数据中台等）
          4.4. 互联网金融：(以合规为底线，通过场景渗透与智能风控提升用户信任，最终开放生态实现价值共享。)    
                   1. mvp工具替代(线上化工具+用户教育)。     2. 场景渗透阶段（体验优化）  3. 智能风控阶段+开放生态阶段（规模化扩张） 
          4.5. 传统行业: 以效率为目标，通过流程自动化、数据驱动与智能决策提升竞争力，最终重构产业生态    
                   1. mvp流程自动化阶段（单点突破+标准化建设); 2. 数据驱动阶段（体验优化） 3. 智能决策阶段（规模化扩张）  4. 生态重构阶段（持续演进）
5. 技术实现支撑业务迭代时：
          5.1. 技术演进的核心方法论是 **“以业务价值为锚、体系化设计为骨、小步验证为肌、风险兜底为脉、能力沉淀为魂”**， 
                   1. 目标层：以业务北极星为锚，不做无价值的技术； 根据业务阶段做技术迭代。
                           1. 第一步：拆解业务核心诉求（明确 “技术要解决什么问题”）。业务诉求分类：
                                         - 快速验证型（如 MVP 阶段的功能落地）：核心诉求是 “开发快、成本低、易调整”；
                                         - 性能支撑型（如电商大促、评论系统 10 万 QPS）：核心诉求是 “高并发、低延迟、高吞吐”；
                                         - 稳定性保障型（如金融支付、医疗数据）：核心诉求是 “高可用、数据安全、容错性强”；
                                         - 扩展适配型（如多业务线接入、全球化）：核心诉求是 “模块化、可配置、跨场景兼容”；
                                         - 成本优化型（如成熟期系统）：核心诉求是 “资源利用率高、运维成本低”。
                           2. 第二步：评估当前阶段的约束条件（明确 “技术能用到什么程度”）
                                         - mvp阶段： 可接受小范围故障、功能简化      技术选型：轻量、开源、快速落地
                                         - 优化阶段： 零核心故障、体验达标           技术选型：聚焦瓶颈、渐进优化
                                         - 规模化阶段：高可用性、低边际成本          技术选型：分布式、可扩展、自动化
                           3. 第三步：筛选技术候选池（明确 “哪些技术能满足需求”）
                   2. 设计层：体系化拆解，分阶段落地，不搞大爆炸式重构；（总体拆解框架：按 “业务层->技术层->团队能力层"） 
                           1. 优先级决策工具： 按 “价值 - 风险矩阵(先做 “高价值低风险”，规避 “高风险低价值”)
                           2. 时间规划工具：   按 “业务时间节点” 和 “事项优先级” 拆分
                           3. 落地执行工具 ：  按 “流程 - 责任矩阵拆分(按 “技术演进全流程” 和 “责任方” 拆分，明确每个环节的 “Owner、交付物、时间节点、依赖项”)
                   3. 执行层：小步验证，灰度推广，用数据驱动决策；
                   4. 风险层：提前兜底，故障演练，确保业务不中断；
                             1. 技术演进必然伴随风险（如技术选型失败、业务中断、数据不一致），P7 必须提前设计 “兜底机制”，确保风险可控：
                   5. 沉淀层：组件复用，规范落地，团队赋能，让价值持续放大。
          5.2. 基础系统迭代：1. 核心功能上线；   2. 提升性能和稳定性。 3. 支持高并发与平台化扩展

   
### 每当做一个新需求时，就要想到
1. 需求的入口出口，完整的生命周期是什么样的
2. 有没有横切需求
3. 稳定性专项
      3.1. 流量模型(流量是什么样的，容量评估)
      3.2. 改造对应场景 是否涉及核心链路修改 是否可以逻辑或者数据冗余进行快速止损 不同场景是否做了隔离
      3.3. 补偿，重试，延迟执行，同步转异步
      3.4. 限流、熔断，限制连接数，限制内存使用
      3.5. 能否人工降级
      3.6. 是否可快速失败  
      3.7. 是否可故障转移 故障转移是否可自动回恢复
      3.8. 是否有预案，预案是否可自动执行


### 流量模型
1.1.1 爆发-瞬时高峰型(秒杀、限时抢购、限量发售)
        特点：持续时间短，峰值极高，可预测性强(限时)
        策略：提前预热服务；服务器资源要按峰值QPS准备，安全系数建议2倍以上；准备服务降级方案
1.1.2 波浪型-持续高峰型 (大型促销活动（如双11、618）、持续多日的优惠活动)
        特点：在活动期间，流量持续处于高位； 规律性：小高峰常出现在整点、午休、下班后等时段
        策略：弹性伸缩，按需扩容
1.1.3 爬坡型-渐进增长型 (内容发布，社交裂变等)
        特点：没有瞬间的冲击，但总量可能很大。 先逐步增长到一个稳定的高峰，然后缓慢下降。
        策略：实时监控流量增长趋势，逐步扩容
1.1.4 长尾型-持续稳定型 (长期有效的优惠券、会员日、常规促销)
        特点：像“长尾巴”。活动期间流量平稳，但持续时间很长；稳定性要求高：系统需要长时间稳定运行。
        策略：适度扩容：按预估的平均流量增加固定数量的机器。关注资源消耗：长期运行下，数据库连接、内存泄漏等问题更易暴露。
1.1.5 周期波动型(每日签到，每日任务，周期性活动任务)
        特点：高峰时间点非常固定，像锯齿一样涨跌。总访问量和qps可控
        策略：定时伸缩(定时任务自动扩缩容)，轻量级应对: 不需要大规模扩容，只需优化性能即可。

### 新增一个运营活动时，该加多少机器
1. 明确活动目标和预期 (活动是什么类型的, 不同类型，有不同的流量特点)
   1.2 活动目标有哪些关键指标 (参与人数，最高qps，dau，还是关键业务指标增长)
           参与人数有多少，时间持续多长，可以评估出总体需要的qps和吞吐量，高峰qps
2. 评估现有容量
   2.0. 查看3-6个月监控，分析日常峰值和节假日峰值的资源使用率（CPU、内存、磁盘IO、网络带宽）
   2.1. 进行基准测试和压力测试，评估基准 单机/整体 的最大的qps，响应时间，资源利用率等
   2.2. 压力测试下定位到最大能力，并分层监控每一层的性能拐点(web层，缓存层，mq层，redis层，db层，三方依赖等)
         2.2.1. web层评估方法：最大qps数，关键指标：cpu，内存，连接数
         2.2.2. 缓存层评估方法：最大qps数，连接数，maxmemory， 关键指标：缓存命中率，内存利用率
         2.2.3. 数据库评估方法：tps，最大连接数，iops， 关键指标：慢查询，主从延迟时间，所等待
         2.2.4. 消息队列评估方法：吞吐量，消息堆积量
         2.2.5. 三方服务依赖：评估方法：问相关开发，最大qps，限流降级策略等。
3. 分层计算容量缺口
   3.1 web层应对流量洪峰
   3.1.1计算平均qps(按一天4w秒算)峰值qps(平均和峰值按28比例或者查看监控)
   3.1.2 根据单机的qps 进行计算需要多少机器
   3.2 缓存层（Redis）：预估缓存容量和连接数。
   3.3 数据库层：最脆弱，需重点评估。
   主从复制、读写分离？
   是否需要分库分表？
   连接池大小调整？
4. 制定扩容方案
   4.1 垂直扩容(升级单台机器配)
   4.2 水平扩容(加机器)
   4.3 混合方式
5. 风险与应对措施(稳定性)
   5.1 数据库瓶颈：
          措施：提前做读写分离、增加只读实例、优化慢查询。
   5.2 缓存击穿/雪崩：
         措施：设置合理的缓存过期策略、使用布隆过滤器、缓存预热。
   5.3 依赖服务限流：
         措施：评估第三方API（如支付、短信）的调用配额，申请临时提升。
   5.4 网络带宽：
         措施：检查带宽是否足够，特别是CDN流量。
   5.5 监控与告警：
        措施：部署全方位监控（应用、主机、数据库），设置关键指标告警（CPU>80%，QPS突增等）。
   5.6 回滚预案：
       措施：准备快速回滚到扩容前状态的方案。
6. 执行与验证
   提前扩容：在活动开始前至少24-48小时完成扩容。
   全链路压测：模拟活动流量，验证系统整体性能。
   灰度发布：先对部分机器部署，观察稳定后再全量。
   活动期间值守：运维、开发团队现场或随时待命。



技术需求与业务需求的不同
1. 技术需求(url短链系统设计)的 “业务价值直接通过技术能力体现”，技术四要素(高性能、高可用、低成本、可扩展)是 “业务价值本身”； 
2. 业务类需求（作业系统）的 “业务价值通过解决用户痛点体现”，技术四要素是 “实现业务价值的保障”，而非 “价值本身”。

### 实现500万数据每天插入： 核心是平衡写入性能、查询效率、存储成本和高可用
1. 需求拆解,业务抽象： 数据特征(结构化/半结构化，单条数据大小)， 写入模式(实时单条写入，批量准实时写入, 峰值qps)，查询模式(oltp / olap，延时)， 数据生命周期(冷热数据，是否归档)， 数据一致性(数据丢失，重复数据)
2. 架构分层设计：“接入层→写入处理层→存储层→计算层→查询层→归档层”
3. 技术选型： 接入层(前端埋点http上报 -> 服务端kafka缓冲峰值流量)  --> 写入处理层(flink进行实时处理) --> 存储层(mysql, doris) --> 计算层(实时flink + 离线spark) --> 查询层(统一接口，缓存加速)

5. 优化策略： 写入优化， 查询优化， 存储优化(数据压缩，冷热分离), 扩展性设计
6. 监控告警： 接入层(kafka消息堆积量，生产消费速率，副本同步延迟时间)  --> 写入处理层(处理延迟，数据处理量， 失败次数，checkpoint成功率) --> 存储层(mysql活跃线程数，写入 QPS、查询 QPS、连接数、慢查询数) --> 计算层(Flink/Spark：CPU / 内存使用率、任务运行状态、聚合结果输出速率) --> 查询层(接口耗时，缓存命中率，数据库查询次数)

### 练习记录里批改结果字段过大，优化需求。
1. 需求拆解，进行业务抽象： 
       1.1. 将 “具体需求” 转化为 “技术模型”， 考虑哪些纬度(用户体验，业务功能，系统稳定性，成本约束)
       1.2. 抽象为可量化的技术模型，核心是输出 3 个关键文档： 数据画像， 查询模型，核心约束。
                1. 数据画像： 结构化小字段（1KB）+ 大 JSON（1K-200K，含答题详情），日写入 10 万条，查询 QPS 峰值 1000+，生命周期 3 年（7 天热、30 天温、其余冷）。
                2. 查询特征：Q1：学生查近 7 天练习列表（高频，延迟≤50ms）； Q2：学生查 1 年前练习的完整 JSON（低频，延迟≤1s）； Q3：教师统计某班级错题率（中频，延迟≤5s）。
2. 技术选型： 维度评估→建立 “多维度决策矩阵”，拒绝 “单一指标最优”
            关键决策：  热数据（7 天内）：查询延迟权重最高（30%），Redis 总分 3.9 最优，虽成本高（1 分），但可通过 “短保留期” 控制总成本；
                      冷数据（30 天 +）：存储成本权重最高（25%），OSS 总分 3.95 最优，虽延迟一般（2 分），但低频查询可容忍；
                      最终方案：“Redis（热）+ OSS（冷）” 组合，加权总分最优，且覆盖所有业务约束
3. 架构分层： “结构化拆分 + 冷热分离 + 多存储协同” 。按 “数据生命周期” 拆分，拒绝 “单一存储通吃”， 热数据redis -> 温数据 redis+oss -> 冷数据 oss归档
4. 关键设计： 风险管控→“前置预判风险，预留应对方案”
5. 落地演进→“最小化试错，预留扩展接口” P7 的设计不是 “一次性交付”，而是 “可演进的框架”—— 先落地最小可用版本（MVP），验证核心假设后再迭代，同时预留扩展接口，避免未来重构成本过高。
    5.1. MVP 阶段（1-2 周），核心功能可用
           落地核心功能：MySQL 存结构化字段 + Redis 存 7 天热 JSON+OSS 存 30 天冷 JSON；
           验证核心假设：Redis 延迟是否≤50ms？OSS 冷数据访问是否可容忍？
           监控指标：Redis 缓存命中率、OSS 访问延迟、MySQL 写入 QPS。
    5.2. 迭代阶段（1-3 个月），提升性能和稳定性
           优化 1：若 Redis 缓存命中率＜80%，调整热数据保留期（如从 7 天改为 14 天）；
           优化 2：若部分 JSON 超 500KB，新增 “Redis+OSS 二级存储”（大 JSON 存 OSS，Redis 存 URL）。
    5.3. 演进阶段（6-12 个月）， 支持高并发和 业务扩展性
           若数据量翻倍至日增 20 万条：Redis 扩容至 6 主 6 从，OSS 自动扩容（无需操作）；
           若需教师全文检索：新增 ES 集群，同步 MySQL 数据构建索引，不影响现有存储架构。

### 设计一个短链系统(技术需求)
> 核心不是 “实现短链生成与跳转” 的基础功能，而是构建 “高性能、高可用、低成本、可扩展” 的服务架构，同时兼顾业务演进（如统计分析、权限控制）和极端场景（如流量暴增、恶意攻击）。
1. 需求拆解，业务抽象：首先会将 “短链系统” 的模糊需求，转化为可量化的技术模型，明确 “必须满足什么” 和 “可以妥协什么”
      1.1. 核心业务场景(频率，核心诉求)：短链跳转(90%业务，要求用户无感知)，短链生成(5%，要求生成不重复)， 短链统计(4%,支持uv/pv)， 短链删改(1%, 权限控制，防止恶意)
      1.2. 数据画像： 核心数据(有哪些字段)，url字段特征， 增删查改时注意的点(上面创建数据表时的思路)
      1.3. 不可妥协的约束： 全年可用性， 一致性(短链一旦生成，跳转结果必须唯一且不变)， 安全性(防止短码被暴力猜测), 成本
2. 纬度评估：核心技术点决策矩阵（权重由业务优先级决定）
      2.1. 短链生成策略： 短链存储方案， 短链统计方案， 高可用架构
      2.2. 跳转性能权重最高（30%），必须用 Redis 缓存热点短链；
      2.3. 统计数据属于时序型（20%），InfluxDB 比 MySQL 更适合高写入 + 按时间范围查询；
3. 分层设计：按 “流量链路” 拆分，隔离不同维度问题。 按 用户 → 接入层 → 业务层 → 数据层 → 基础设施层
      3.1. 接入层：挡在最前面的 “门卫”(核心职责：流量控制、安全防护、初步路由)
      3.2. 业务层：模块化拆分，各负其责(核心职责：短链生成、跳转、统计、管理，按 “高内聚低耦合” 原则拆分为 4 个模块（但部署为单体，降低复杂度）：)
      3.3. 数据层：按 “数据特性” 选存储，拒绝 “一刀切”(核心职责：高效存储和查询不同类型的数据)
             1. 短链映射(redis+mysql), 2.访问统计(时序数据库)， 3.操作日志
      3.4. 基础设施层: 核心职责：确保系统稳定运行，问题可追溯,(id生成器，监控报警，压测与预案)
4. 风险管控：预判极端场景，提前留好 “后路” 
      4.1. 风险类型(短码冲突，流量暴增，缓存雪崩，恶意攻击)， 应对场景(mysql唯一键+id自增防冲突， redis扩容放暴增， 防雪崩与雪崩兜底， ip封禁与短码长度提升防恶意)
      4.2. 形成 “风险识别→应对策略→责任方→复盘机制” 的闭环
5. 落地演进
    1. MVP 阶段（1 个月）：核心功能可用
       实现：短链生成 + 跳转 + 基础统计（UV/PV）；
       技术栈：模块化单体服务（Spring Boot）+ Redis（单节点）+ MySQL（单库分表）；
       目标：验证 “短码生成唯一性”“跳转延迟≤50ms” 两个核心假设；
       监控：接入基础监控（跳转成功率、平均延迟）。
   2. 迭代阶段（3 个月）：提升性能与可靠性
      新增：CDN 接入、Redis 主从、MySQL 主从、访问统计多维度分析；
      优化：缓存策略调优（提高命中率至 95%+）、短码生成性能优化；
      目标：支撑 QPS 1 万 +，可用性 99.9%；
      验证：压测极端场景（如 10 万 QPS 持续 10 分钟）。
   3. 规模化阶段（6 个月后）：支撑高并发与业务扩展
      升级：Redis 集群（3 主 3 从）、多活部署（南北双机房）、统计分析独立服务；
      扩展：支持自定义短码、权限控制、白名单、过期自动删除；
      目标：支撑 QPS 10 万 +，可用性 99.99%；
      演进：模块化单体拆分为微服务（生成 / 跳转 / 统计独立部署）。

### 如何排查线上问题(分层排查，p7级)
1. 紧急止血（0-5 分钟）：优先保障用户可用，不纠结根因
        不管原因，先扛住当前压力：临时扩容 / 限流 / 降级非核心功能  网络层(临时提额带宽) -> 应用层(增加实例,提高cpu/内存) -> 数据库层(紧急释放连接 + 分流)
        回滚可疑变更（最近 1-2 小时的发布、配置修改）。
2. 界定范围（5-10 分钟）：锁定故障边界，减少排查量
        明确错误类型（500/503/504/4xx）；
        确认影响对象（所有用户 / 特定地区 / 某功能模块）；
        关联时间线（是否和发布、流量峰值同步）。
3. 分层排查（10-30 分钟）：全链路扫描，找可疑瓶颈
        按 “网关→应用→数据→依赖→网络” 自上而下排查；
        每个层级看核心指标（如应用层看 CPU / 线程池，数据层看慢查询 / 连接数）。
4. 验证修复（30-60 分钟）：小范围验证后全量落地，监控回稳
        针对疑似根因做 1 个最小变更（如修复 SQL、切换依赖节点）；
        观察 10-20 分钟，确认错误率、RT 恢复正常。
