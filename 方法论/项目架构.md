### 架构整体关系
> 业务架构（定业务目标/逻辑）→ 系统架构（定整体技术框架，含应用/技术/数据等子架构）→ 应用 / 服务（具体实现）
1. 业务架构是架构体系的起点，聚焦 “业务应该如何运作”，不涉及具体技术。
       核心关注与产出：
              1. 业务目标与价值链（例如：电商平台的 “用户增长→转化→复购” 价值链）；
              2. 业务流程模型（例如：订单履约流程 “下单→支付→库存扣减→物流发货”）；
              3. 业务域划分（例如：电商拆分为 “用户域、商品域、订单域、支付域”）；
              4. 业务规则与指标（例如：“满 200 减 50” 的促销规则、“订单转化率≥30%” 的业务指标）。
2. 系统架构是整合性框架，“技术层面的总纲”，把应用架构、技术架构、数据架构、部署架构等整合起来，形成统一的技术框架。
      核心关注与产出：
              0. 应用架构
              1. 技术总框架(大单体+tomcat部署， 微服务+k8s部署，Serverless + 云函数部署方式等)
              1. 全局技术层级（前端→API网关→应用层→中间层→数据层）；
              2. 技术架构在技术层级的基础上，明确每个层级的具体技术选型（如前端用 Vue、数据层用 MySQL+Redis）。
              3. 数据架构
              4. 部署架构
3. 应用架构是业务架构的 “数字化载体”，聚焦 “通过哪些应用系统 / 模块来承载业务流程”，解决 “业务功能由谁实现” 的问题，连接业务与技术的桥梁。
      核心关注与产出：
              1. 应用系统划分（例如：电商平台拆分为 “用户中心、商品管理系统、订单系统、支付系统、物流系统”）；
              2. 应用间交互关系（例如：订单系统需调用支付系统完成付款，调用物流系统创建物流单）；
              3. 应用功能模块（例如：订单系统包含 “订单创建、订单查询、订单取消、退款处理” 模块）；
              4. 接口规范（例如：订单系统与支付系统的 “支付结果回调” 接口定义）。
4. 技术架构是应用架构的 “底层支撑”，聚焦 “技术栈选型、基础设施、部署架构”，解决 “如何稳定、高效地运行应用系统” 的问题，纯技术视角。
     核心关注与产出：
              1. 技术栈选型：前端（Vue/React）、后端（Java/Go/Python）、数据库（MySQL/PostgreSQL）、中间件（Redis/MQ）；
              2. 基础设施：服务器（物理机 / 云主机）、网络（VPC、负载均衡）、存储（云存储 / 本地存储）；
              3. 部署架构：单机部署、集群部署、微服务部署、容器化（Docker/K8s）、云原生架构；
              4. 非功能保障：高可用（多活部署、故障转移）、高性能（缓存、异步）、可扩展性（弹性伸缩）。
      例子：电商平台的技术架构可能是 “K8s 容器化部署 + Spring Cloud 微服务 + MySQL 主从 + Redis 缓存 + RocketMQ 异步通信”。
5. 数据架构聚焦 “业务运作中产生的数据”，解决 “数据从哪里来、存在哪里、如何流转、如何保障质量” 的问题，是企业 “数据资产化” 的核心支撑。
     核心关注与产出： 数据采集层， 数据存储层， 数据加工层， 数据服务层。
6. 部署架构：聚焦 “应用、服务、基础设施如何部署、调度、容灾”
     核心关注与产出：
              1. 分层级的部署： 前端，app，后端服务，基础服务，mysql等部署、环境、区域、策略 问题
              2. 调度问题： 如何应对高并发（弹性扩容、负载均衡）
              3. 容灾问题： 如何保证高可用（主从复制、多区域、多节点部署，避免单点故障）


### 企业级架构 -> 业务线架构 -> 项目架构 -> 模块架构
> 范围层级：从公司级→业务线级→项目级，覆盖范围逐渐缩小，架构颗粒度逐渐变细（公司级定 “规则”，业务线级定 “方案”，项目级定 “执行细节”）；
  设计维度：每个范围层级都包含 “业务架构→系统架构→应用架构→技术架构”，且上层设计维度约束下层（如公司级技术栈约束业务线级和项目级）；
1. 企业级架构需要 避免各业务线重复建设和技术孤岛。核心目标：
                1. 制定全局标准、统一技术栈、
                2. 规划核心基础设施（如数据中台、技术中台），
2. 业务线架构的核心目标：
                1. 承接企业级架构要求，设计该业务线内的整体架构，
                2. 明确业务线内的系统边界、核心流程和跨系统交互规则。
3. 项目架构的核心目标：
                1. 按企业级和业务线级架构约束，
                2. 设计项目专属的落地方案，明确模块拆分(应用子架构)、技术选型(技术子架构)、接口设计、部署方案等细节。
4. 模块架构的核心目标：
                1. 聚焦模块内部的设计细节，确保模块高内聚、低耦合，符合编码和复用要求。


### 业务域(业务规划) -> 应用系统(系统载体) -> 服务(功能单元)
1. 业务域与应用：“业务规划” 与 “系统载体” 的对应关系
    1. 主流是1V1的关系
    2. 商品域业务复杂，1V3(商品管理，库存管理，搜索管理)，
    3. 售后域简单 2V1(售后，评价，合并)
2. 应用与服务：“系统载体” 与 “功能单元” 的拆解关系
    1. 单体架构中，“应用” 是核心载体，“服务” 是应用内的功能模块（不可独立部署），适合业务简单、规模小的场景；
    2. 微服务架构中，“应用” 是业务域的载体，“服务” 是可独立部署的最小功能单元，适合业务复杂、高并发、需快速迭代的场景；



### 数据中台
1. 数据中台的本质： **“以业务为核心的数据价值变现体系”** 
2. 解决的痛点问题：
       1. 数据孤岛： 各个业务线数据没打通
       2. 重复建设： 各个业务线各自一套
       3. 价值难落地： 报表、分析滞后于业务需求，或无法直接支撑业务决策 
3. 核心能力：
       1. 统一数据接入（采集层）： 通过标准化接口，统一采集 结构化，半结构化，非结构化数据。
       2. 数据治理与资产化（加工层）： 数据清洗， 数据建模
       3. 数据服务化（输出层）： 封装统一调用的api接口、报表/bi服务、算法服务
       4. 数据治理与监控（保障层）： 安全治理，质量治理，生命周期治理
4. 接入方式：
       1. 从业务痛点切入（如先解决 “用户标签复用” 问题）→ 小步快跑迭代（3-6 个月出成果）→ 逐步扩展场景。
5. 注意问题：
        1. 保障中台运转的 “制度保障”，：  跨部门的数据团队（如数据产品经理、数据开发、数据分析师）、
                                      数据治理规范（如数据口径统一、质量监控）、
                                      业务协同流程（如需求提报 - 数据开发 - 服务交付的闭环）。
        2. 数据中台的难点本质是 “非技术问题”
               1. 组织协同的阻力(业务团队要求快，技术团队要架构稳)
               2. 数据治理的复杂度(数据质量问题， 数据口径统一问题，比如对于日活的定义等)
               3. 业务落地的适配性(需要持续快速的支持业务)
               4. 持续运营的动力
6. 数据仓库对比
     数仓是 “企业的后视镜”（回顾过去、辅助决策），数据中台是 “企业的导航仪”（指导现在、驱动业务）。
       1. 数据仓库是T+1的，只以报表形式展现， 单向：业务系统→数据仓库→报表 / 分析
       2. 数据中台是实时 + 离线（毫秒级，如实时推荐），双向：业务系统→中台加工→服务反哺业务


### 技术中台
技术中台是企业级的技术能力复用与支撑平台，核心是把各业务线通用的技术能力（如开发框架、中间件、基础服务）沉淀成标准化组件，
让业务团队不用重复造轮子，聚焦核心业务创新，本质是 “技术能力的集约化供给”。
