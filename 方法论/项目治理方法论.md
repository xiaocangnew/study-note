### 项目治理
> 软件研发与维护中的项目治理，本质是通过 “规则化、透明化、可追溯” 的机制，解决项目全周期中的 “目标偏差、流程混乱、质量失控、风险突发、资源浪费” 等问题。
1. 数据治理(目标偏差)
    1.1. 并非单纯 “收集数据”，而是建立 “目标 - 指标 - 分析 - 行动” 的闭环
    1.2. 需覆盖全生命周期（从立项到迭代优化） 和全角色（业务、产品、开发、测试、运维），形成一套分层、可落地的指标体系
            1.2.0. 业务相关指标(核心功能使用率=用过的人/总活跃人， 用户留存率（次日/7日）； 具体业务指标 )
            1.2.1. 产品相关的指标(文档完整性评分，文档变更率，业务价值密度，沟通效率指标=评审耗时/写文档时间)
            1.2.2. 开发相关的指标(人均有效产出，迭代交付率，任务完成周期， 单元测试覆盖率，代码审查通过率)
            1.2.3. 测试相关的指标(缺陷密度， 缺陷修复及时率，缺陷逃逸率，功能覆盖率，)
            1.2.4. 运维相关的指标(稳定性相关的可用性SLA，平均恢复时间MTTR, 响应时间RT， 每秒事务数，安全漏洞修复周期)
    1.3. 落地数据思维的关键步骤
            1.3.0. 口径唯一，对齐每个指标的定义，避免各个业务方统计口径不一样。
            1.3.1. 对齐每个指标的业务意义。例如，“单元测试覆盖率”的目标不是“达到80%”，而是“通过覆盖核心代码减少50%的线上bug”。
            1.3.2. 聚焦 “关键少数指标”：每个阶段选择 3-5 个核心指标，避免指标过多导致团队精力分散
            1.3.3. 建立 “数据采集” 机制：确保数据准确、自动
                           任务 / 需求数据：Jira、飞书项目、TAPD（采集迭代交付率、需求变更率等）；
                           代码数据：GitLab、GitHub（采集代码提交频率、单元测试覆盖率、CR 通过率等）；
                           测试数据：TestRail、禅道（采集缺陷密度、测试覆盖率等）；
                           线上数据：Prometheus（性能指标）、ELK（日志）、Sentry（错误监控）、埋点工具（用户行为指标）。
            1.3.4. 持续 “优化指标体系”：适配项目阶段变化
                           指标不是 “一成不变” 的：例如，项目从 “0-1 启动期” 到 “1-10 迭代期”，指标重心需从 “技术可行性” 转向 “业务价值”（如启动期关注 “技术复杂度评分”，迭代期关注 “核心功能使用率”）。
                           淘汰无效指标：若某个指标长期无波动（如 “需求评审耗时占比稳定在 10%”）或无法关联到行动（如 “代码行数” 仅代表工作量，不代表质量），则应淘汰，避免资源浪费。
2. 流程与协作治理(流程混乱)
     2.1. 研发流程(prd5稿 -> 负责人介入 -> prd9稿 -> 研发介入 -> 设计方案确定 -> 排期 -> 研发 -> 测试 ->上线。 固定prd周期，固定开会周期)
     2.2. 需求变更流程(需建立 “变更申请 - 影响评估 - 审批 - 落地” 的闭环流程)
     2.3. 线上问题发现&解决流程
     2.3. 项目排期
3. 质量治理(质量失控)
     3.1.1. 代码质量(静态检查工具，code review，项目负责人制度)
     3.1.2. 测试质量(单元测试，集成测试，压力测试，线上回归测试)
     3.1.3. 上线质量(灰度发布，报警日志监控，蓝绿发布)
4. 项目问题治理(风险突发)
     4.1. 性能治理
           4.1.1.数据库性能(慢sql，sql超时，连接池耗尽，死锁， 大事务)
           4.1.2. 接口性能(接口耗时分析，接口抖动分析)
           4.1.3. 缓存性能(Redis 响应慢、缓存穿透 / 雪崩、内存溢出)
     4.2. 稳定性治理
           4.2.1. 故障预防(单点问题改为高可用架构，依赖服务增加熔断降级)
           4.2.2. 告警治理(告警分级，噪声消除)
           4.2.3. 故障应急(应对流程,包括因为bug导致的和因为流量导致的)
           4.2.4. 容灾
     4.3. 安全治理
           4.3.1. 合规性， 
           4.3.2. 安全开发(开展安全需求分析,如用户密码需加密存储; 使用工具检测 “SQL 注入”“XSS 跨站脚本” 等常见漏洞; 模拟攻击等).
           4.3.3. 规范敏感数据处理（如用户身份证号需脱敏存储，传输需加密），限制数据库访问权限（仅核心人员可查看原始数据）。
     4.4. 遗留问题治理
           4.4.1. 重构问题，hack问题，记录的待优化项.
           4.4.2. 依赖治理
           4.4.3. 配置治理
           4.4.4. 接口治理(接口分散等)
5. 技术资产与资源治理(资源浪费)
     5.1. 技术资产复用与管理
            5.1.1. 公共组件库，公共能力抽象
            5.1.2. 文档管理：要求输出 “可落地” 的文档
     5.2. 资源分配与管控
            5.2.1. 环境资源：规范开发 / 测试 / 预发布 / 生产 “四套环境” 的配置标准
            5.2.2. 优化资源利用率(部署机器资源,存储资源,缓存资源)



### 项目研发流程中的风险治理 (项目 Owner 的 “风险管控四步法: 全面梳理 -> 优先级排序 -> 指定预案 -> 持续监控)
1. 需求阶段的风险
     1.0. 需求与业务目标脱节(项目启动时，明确「业务目标对齐文档」：将需求与业务指标绑定, 绑定相关数据指标)
     1.1. 需求模糊不完整(组织各方进行反提问，细化需求细节，明确验收标准)
     1.2. 需求频繁变更(明确变更流程，优先核心功能，预留工期缓冲时间)
2. 技术与架构阶段
     2.1. 技术选型问题(技术成熟度，团队熟悉度，性能，成本)
     2.2. 技术架构问题(输出架构图并组织评审；针对高并发、高可用场景，提前设计 “限流、熔断、降级” 方案；预留架构演进空间 )
     2.3. 技术债务问题(指定规范和工具做代码质量扫描，减少硬编码； 建立「技术债务清单」：记录债务内容、影响范围、修复优先级； )
3. 人力与资源
     3.1. 团队技能不匹配(项目启动前做技能矩阵盘点； 针对技能缺口，提前安排分享培训)
     3.2. 核心人员请假离岗(推行知识共享机制定期组织内部分享培训；核心模块安排2人以上熟悉（如A为主开发，B为辅开发，参与代码走查和测试）)
     3.3. 资源不足(硬件 / 工具 / 外部依赖)
          3.3.1. 提前输出「资源需求清单」：明确需要的服务器配置、开发工具（如 Jira、Jenkins）、第三方服务（API、SDK），并确认资源到位时间；
          3.3.2. 对外部依赖（如第三方 API），提前明确接口规格、稳定性保障和故障响应时间；同时开发 “降级方案”（如第三方 API 不可用时，用本地模拟数据替代）
4. 进度与质量管控阶段
    4.1. 进度估算失误 (按功能点进行拆分，增加缓冲时间)
    4.2. 缺乏有效进度监控(每日站会, 用jira跟踪任务状态，设定关键里程碑（如 “需求评审完成”“开发提测”“灰度发布”）；每周输出「项目周报」：量化进度（如 “总任务完成率 70%”）、问题和下周计划)
    4.3. 测试不充分(明确测试类型和覆盖范围； 测试提前至代码开发前；单元测试通过才能提交代码；冒烟测试通过才能提测)
5. 外部依赖与环境风险
    5.1. 政策合规风险
          5.1.1. 提前与监管部门沟通，确认方案合规性; 咨询法务：梳理业务涉及的合规要求; 
          5.1.2. 开发过程中同步做合规测试
    5.2. 市场突发风险
          5.2.1. 市场竞品分析,并定时跟踪竞品动态; 
          5.2.2. “柔性需求方案”：核心功能（如下单、支付）按原计划开发，非核心功能（如营销活动）预留扩展接口，便于快速响应市场变化; 
          5.2.3. 与业务方约定 “市场变化应对机制”：若竞品出现重大动作，24 小时内召开紧急会议，评估是否需要调整需求或优先级。)
6. 安全与运维风险
    6.1. 系统安全漏洞
           开发前学习「OWASP Top 10」（常见 Web 安全漏洞清单），
           代码开发时遵循安全规范（如接口加 Token 校验、输入参数过滤）；
    6.2. 建立 “安全监控与响应机制”
           线上部署日志审计工具（如 ELK）和入侵检测系统（IDS），一旦发现异常（如多次失败登录、大量数据下载），立即触发告警并启动应急预案（如封禁 IP、隔离服务器）。


### 治理屎山代码( 比如拍批服务，里面各种逻辑看不懂，没注解)
> 作为项目 Owner，处理此类问题的核心不是 “追求技术完美”，而是 “在保障业务稳定的前提下，用最低风险解决最紧急的问题”。
1. 第一步：“止血”  短期（1-3 个月）  —— 先控制代码债务恶化，保障新需求交付
     1.1. 制定新需求开发规范：隔离新代码与旧代码
            1.1.1. “新功能新模块” 原则
            1.1.2. “旧代码最小改动” 原则 (若新需求必须修改旧代码，强制 “新功能独立封装”, 仅修改 “必要逻辑点”,不重构周边代码；修改前必须先写 “影响范围分析”并补充单元测试)
            1.1.3. 文档先行原则
     1.2. 建立 “旧代码维护手册”：降低理解成本
            1.2.1. 核心业务流程：用流程图梳理
            1.2.2. 高危模块清单：标记 “看不懂但线上稳定” 的模块, 注明 “禁止随意修改，如需改动需全员评审”
            1.2.3. 历史坑点记录：收集过往维护中遇到的问题
     1.3. 优化测试与发布流程：降低新需求上线风险
            1.3.1. 针对涉及旧代码修改的需求，由测试团队做 “全链路回归测试”，并增加 “灰度发布” 环节 
            1.3.2. 制定 “回滚预案”：所有涉及旧代码的发布，必须提前准备回滚包
2. 第二步：“体检”    —— 系统梳理技术债务，明确治理优先级
       > 在保障新需求交付的同时，需系统性分析代码混乱的根源，避免 “盲目重构”。
       > 核心是 “用数据说话”，而非凭感觉判断 “哪个模块该改”
     2.1. 技术债务盘点：量化问题维度 （组织团队（开发 + 测试 + 架构师）从 4 个维度对旧系统做全面盘点，输出《技术债务清单》：）
            2.1.1. 维护成本 (近 3 个月新需求中，涉及该模块的平均工期（如 “订单模块每次改动需 5 天，其他模块仅 2 天”）)
            2.1.2. 业务价值 (模块是否支撑核心业务)
            2.1.3. 风险程度 (模块是否有潜在 bug（如 “无事务控制，高并发下可能数据不一致”）、是否依赖过时技术（如 Java 6）)
            2.1.4. 重构难度  (模块代码量（如 1 万行 vs 10 万行）、是否有测试用例)
     2.2. 划分治理优先级：“先易后难，先核心后边缘”
            2.2.1. P0（紧急治理）：核心业务模块 + 维护成本极高 + 重构难度低
            2.2.2. P1（迭代治理）：核心业务模块 + 维护成本中等 + 重构难度中等
            2.2.3. P2（暂缓治理）：非核心业务模块 + 维护成本低 + 风险低
3. 第三步：“渐进式重构” 中期（3-12 个月）—— 小步快跑，风险可控地优化旧代码
        > 采用 “增量重构 + 平行运行 + 逐步切换” 的模式，避免 “一刀切重构” 导致线上故障。
        > 核心逻辑是：“用新代码逐步替换旧代码，确保新旧逻辑并行运行且结果一致，验证无误后再下线旧代码”。
     3.1. 重构实施四步法（以 “订单状态流转模块” 为例）
            3.1.1. 对旧模块的所有业务场景正常流程 + 异常场景写黑盒测试用例（保障重构后功能一致）
            3.1.2. 开发新模块（遵循新规范）
            3.1.3. 平行运行 + 对比验证 (线上部署但不直接对外提供服务，而是让 “旧模块处理真实流量，新模块同步接收相同的请求并处理（但不写入数据库，仅输出日志）”。通过日志对比新旧模块的处理结果)
            3.1.4. 灰度切换 + 逐步下线 (验证无误后，通过配置中心（如 Nacos/Apollo）控制流量比例, 有问题立马回切)
     3.2. 重构中的关键原则
            3.2.1. “不追求完美，先解决核心问题”
            3.2.2. 重构与业务需求结合”
            3.2.3. “避免重构期间做架构大调整”
4. 第四步：“强身”  长期（1 年以上）—— 建立长效机制，防止代码债务复发
     4.0. 建立编码与评审规范
     4.1. 完善测试与监控体系
     4.2. 知识沉淀与团队赋能
            4.2.1. 定期组织 “代码复盘会”：每月针对 1-2 个重构模块，分享 “重构前的问题、重构思路、踩过的坑”，让团队理解 “为什么这么改”，而非单纯执行。

### 架构不合理的ddd治理
> 架构不合理的主要表现
1. 服务边界模糊  ：一个业务流程需要改 3-5 个服务（如 “修改订单优惠规则” 需改订单、商品、用户、优惠券 4 个服务），且改动逻辑分散
2. 核心域被拆分  ：核心业务逻辑（如订单状态流转）分散在多个服务，新需求需跨服务同步修改，易出数据不一致
3. 依赖关系混乱  ： 服务间存在循环依赖（A 依赖 B，B 依赖 A），或 “星形依赖”（所有服务依赖核心服务）
4. 服务职责过载 / 缺失
> 问题诊断： 业务梳理→域划分→边界确定→服务映射
1. 业务全景梳理 —— 搞清楚 “业务到底在做什么，核心价值是什么"
   1.0. 组织业务方（产品 / 运营）+ 技术方（开发 / 架构师）共同梳理,  术语统一
   1.1. 核心业务流程
              用流程图画出 “用户从接触产品到完成价值交付” 的全链路（如电商的 “浏览→加购→下单→支付→履约→售后”），(这个就是用户故事，用例)
              标注每个环节的 “参与者（用户 / 系统）、动作（下单 / 支付）、数据（订单信息 / 商品信息）” (这就是通过名词法和动词法寻找领域概念来构建我们的领域分析模型)。
   1.2. 业务规则与痛点
             记录每个流程的核心规则（如 “下单时需校验库存、优惠券、用户权限”），
             以及当前新需求的痛点（如 “每次改优惠券规则，订单和支付服务都要改”）。
2. 业务域划分  —— 按 “业务职责” 高内聚、低耦合拆分核心域、支撑域、通用域
       2.1. 核心域：决定企业核心竞争力的业务（如电商的 “订单域”“商品域”“支付域”）一般不超过4个。
       2.2. 支撑域：支持核心域运行的业务（如 “用户域”“地址域”“优惠券域”），不直接产生核心价值，但核心域依赖它。
       2.3. 通用域：所有域都可能用到的公共能力（如 “日志域”“通知域”“权限域”），可抽象为通用服务。
3. 确定限界上下文 —— 定义域内的 “最小业务边界” ( **** 对于子域的划分方法，可以分别按照业务和组织两个视角来看 ****)
       3.1. “是否有独立的业务目标”：如订单域可拆分为 “订单创建上下文”“订单履约上下文”“订单售后上下文”，每个上下文解决一个独立问题（创建订单 vs 处理发货 vs 处理退款）；
       3.2. “是否有独立的数据模型”：如商品域中，“商品基础信息（名称 / 图片）” 和 “商品库存” 可分为两个上下文 —— 前者高频读、低频写，后者高频写（下单扣减），模型和访问模式差异大；
       3.3. “团队责任边界”：若一个业务模块由固定团队负责（如 “优惠券核销” 由营销团队负责），可优先作为独立上下文，便于 “团队 - 服务” 对齐（康威定律：系统设计反映组织沟通结构）。
4. 明确聚合根 --串联实体即订单流程/学习任务流程 (界限上下文是 “地图”，聚合根是 “地图上的关键地点”, 先有地图再有地点)
      4.1. 针对每个界限上下文，进一步梳理 “该上下文内有哪些领域对象”“对象之间的业务关系是什么(比如电商中的用户对象，商品对象)
      4.2. 在上下文内设计聚合根与聚合(比如电商里面的订单，串联起所有核心域， 学习机里面就是学习任务，包含内容，练习，拍批结果，总结和推荐等，串联起所有关键节点)
5. 服务映射 —— 将 “限界上下文” 映射为微服务
   5.1. 界限上下文是 “领域逻辑的边界”，确保模型不混乱；
   5.2. 微服务是 “部署运维的边界”，确保系统能独立演化。
   5.3. 一个限界上下文通常对应一个微服务（复杂上下文可拆分为 2-3 个服务，但需避免过度拆分）
> 实施策略：渐进式重构 —— 在业务迭代中 “换血”，不中断服务
1. 标记 “问题服务”，优先保障新需求交付（1-2 个月）
   1.1. 标记 “改动最频繁、影响最大” 的 3-5 个问题服务（如 “订单服务” 因边界模糊每次需求都要大改），作为优先重构对象。
   1.2. 新需求开发时，对问题服务采取 “旧代码改动最小侵入 + 新逻辑使用新服务隔离”：
2. 从 “非核心服务” 开始重构，验证边界（3-6 个月）
   2.1. 优先选择 “支撑域 / 通用域” 的服务（如优惠券服务、通知服务）进行重构 —— 这些服务业务逻辑相对独立，重构风险低，且能快速验证 “新域边界” 是否合理。
   2.2. 新服务开发 -> 双写双读验证 -> 灰度切换 -> 旧服务下线


### 重构治理 VS 领域治理
领域划分是 “搭骨架”，先搞定支撑领域这个 “地基”，核心领域才能更稳；
代码重构是 “填血肉”，先保住核心领域这个 “心脏”，边缘领域才能安全迁移。
