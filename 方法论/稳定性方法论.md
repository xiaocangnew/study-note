### 稳定性建设(方法论)：
> (MECE拆分1-系统生命周期)产品需求、代码开发、运维部署、故障管理等系统全生命周期进行全方位去考量和设计。
> (MECE拆分2-时间线*责任域) 按 “事前 / 事中 / 事后 × 业务 / 技术 / 数据” 拆分
> (MECE拆分3- 故障生命周期) 按事前 / 事中 / 事后 三个维度
> (MECE拆分4- 风险来源) 按内部系统、外部依赖、流量波动、人为操作
> (MECE拆分5- 技术层级) 按照 “基础设施→中间件→应用服务→业务逻辑”
> (MECE拆分6- 保障手段维度) 形成 “预防→监控→容错→恢复→优化” 的闭环

1 从产品角度：主要是故障发生后的兜底策略
2 从代码研发：
      2.0. 首先要对研发层面有一个代码架构规范，例如编码规范，api规范， 技术文档规范、项目层次规范、模块规范、依赖规范、log规范等  
      2.1. 设计阶段：高可用的架构设计， 做架构分层(接入层，应用层/服务层，数据层)，每一层做好各自的高可用
              2.1.1. 接入层： 域名高可用(防止ddos，使用https防dns劫持)，api的安全，限流与防刷策略。
              2.1.2. 应用层： 无状态设计与水平扩展，幂等设计，容错机制，降级处理机制，
              2.1.3. 数据层： 做好cap，事务性，数据备份与恢复
      2.2. 编码阶段：要有单元测试，代码审查工具等。
      2.3. 运行维护阶段： 针对不同业务场景，专门优化(库存平台稳定性建设实践)
      2.4. 变更机制预防，做好上线审批与周知机制。
3. 从部署运维：
      3.1. 规范上线流程， 要有灰度发布 
      3.2. 监控报警，
4. 从故障管理：
      4.0. 定义指标, (1. 定义可用性指标，99.9%可用性，2. 故障度量考核指标， 3. 服务分级)
      4.1. 故障前，做好容量评估，建立常态化压测， 
      4.1. 故障发现： 完善监控报警管理，进行报警治理，不断优化报警方式指标
      4.2. 故障恢复： 做好应急预案， 切流系统工具
      4.3. 故障总结：复盘总结故障问题，层层剖析问题产生的原因，由表及里分析问题发生的本质。


### 稳定性建设中存在的风险点和难度
1. 存量风险识别的难度.(如何发现这些问题，需要从整体上排除风险,要准确评估整个域的稳定性并识别其中的风险)
        1.1. 日常巡检有助于发现存量风险的苗头，
                  1. 或是慢SQL、或是慢接口，或是cpu突刺。
                  2. 包括业务数据量是否逐步增长到了危险的范围，上下游的调用量是否接近容量上限…
                  3. 各项活动/配置是否临近过期
                  4. 核心业务是否有兜底降级逻辑
                  5. 日志问题
        1.2. 工单和报警(太滞后)。
        1.3. 抓住主要矛盾，先从最核心的业务场景开始治理。
        1.4. 架构治理则对应了对于应用间、甚至整个域内的依赖链路风险评估和治理。
                1. 领域建模、高内聚低耦合、OO等的架构原则，反映到变更风险中，就是控制了变更复杂度。
                2. 资源隔离的架构设计，则是专门用于控制爆炸半径避免相互影响.
2. 风险治理的难度. 
        2.1.排期不够问题
                1. 需要针对本团队业务的重要性、发展阶段、风险情况进行综合评估，确定好稳定性建设在本团队中的重要程度。
                2. 确定好稳定性建设将在团队总投入中的时间占比。这个占比可以在迭代维度进行波动，但周期拉长到季度、年维度的时候，是需要保持在一个符合预期的比例的。
        2.2.治理本身带来的变更风险。 为了预防可能发生的故障，反而引入了变更故障.
                1. 该问题先可以通过架构治理进行分而治之，将大问题拆解成若干个小问题；再通过安全生产规范，控制每次解决小问题引入风险的概率。
3. 增量风险识别的难度.(代码债务阻碍了变更，无论是业务的迭代还是技术的治理，都会提升变更的风险)
         1. 变更可见性,这里所说的可见性，不仅仅是变更执行者本人的知晓，更是整个团队乃至所有相关方共同的认知, 其他同学进行二次确认
         2. 方案可控性，由于整体链路的复杂性和不可控性，对于变更方案的风险可控性评估就显得异常困难。
         3. 人员可靠性： 那么怎样在各种各样的变更中，去保障人员的下限，不要让这种人员的波动性影响到系统的稳定性；甚至尽可能让人员保持他们的高上限
4. 增量风险预防：
        4.1.0. 安全生产规范整个存在的意义就是为了通过流程来控制增量风险。
        4.1.1. 需求变更需要同步所有业务方，共同确认过变更风险。
        4.1.2. 技术管控加码: 技术团队内部的 技改需求、curl、数据订正、Ark变更等操作
        4.1.3. 业务方操作同步：突然执行大量的业务变更操作，突然进行了某项营销活动导致引入远超预期的流量等

### 教育电商履约的稳定性治理
> 核心定义是 **“履约全流程（资源交付、物流配送、服务调度）在各种极端条件下（如开学季高并发、系统故障、突发天气）均能按预期执行，且异常时可快速恢复，不影响用户学习进度”**。
> 学习节点优先保障：稳定性资源向 “关键学习节点” 倾斜（如开学前 1 周、期中 / 期末考试前 3 天），这些时段的系统可用率需达 99.99%（日常 99.9%）；
1. 分场景稳定性保障方案（聚焦核心风险）
     1.1. 课程资源履约（一次性 / 分期）：系统层面 “抗崩 + 防错”
     1.2. 物流履约（一次性 / 分期）：全链路 “抗断 + 兜底”
     1.3. 跨场景共性保障：数据一致性与全链路监控
2. “三横三纵” 闭环体系
     2.1. 按 “风险维度” 建立防御体系
           2.1.1. 技术层防御：解决 “系统崩” 的问题 (“不把鸡蛋放一个篮子”)
                     2.1.1.1. 系统宕机（如开学季课程访问高峰导致服务器崩溃）
                     2.1.1.2. 分级负载与限流：避免 “非核心请求拖垮核心履约”
                                1. 物流履约的 “订单查询接口”是高频非核心请求，系统设置 “每用户每分钟最多查 3 次”，确保开学季发货。
                     2.1.1.3. 缓存分层：解决 “响应慢、数据库压力大” (将履约数据按 “访问频率” 分层缓存（CDN→本地缓存→分布式缓存→数据库）)
                                1. 视频数据存到cdn； 2. 课程已开放的期数存放redis； 3. 物流数据本地缓存15分钟；
                     2.1.1.4. 熔断降级 (应对 “第三方依赖失效”)
                                1. 物流履约依赖顺丰 API，当顺丰 API 超时率达 8%（阈值 5%）时，系统自动熔断顺丰接口，切换至圆通 API，
           2.1.2. 业务层防御：解决 “流程断” 的问题 
                     2.1.2.0. “设计时就假设会出故障”。预设 “物流 API 失效时的手动录入方案。
                     2.1.2.1. 通过 “规则冗余、离线方案、备用资源（如备份仓、电子教材）” 确保业务流程在极端情况下可继续。
           2.1.3. 数据层防御：解决 “数据错” 的问题( “数据可追溯、可校验、可恢复”)
                     2.1.3.1. MQ + 最终一致性的实现多系统履约，确保 “多系统数据一致”
                                1.  “消息可靠投递 + 系统幂等处理 + 失败补偿”
                     2.1.3.2. 对账与校验：发现 “数据不一致 / 错误”
                                1. 每日比对 “关联系统的核心数据”（如订单表 vs 履约表、履约表 vs 物流表），找出差异并修复，
                     2.1.3.2. 幂等设计：防止 “重复操作导致数据错误”
                                1. 对 “可能重复触发的履约接口”（如开通课程、创建物流单）设计幂等性，避免 “用户重复点击导致重复履约”。
                     2.1.3.4. 数据备份与恢复：防止 “数据丢失”
                     2.1.3.5. 数据隐私保护：防止 “敏感数据泄露”
     2.2. 按 “时间维度” 建立闭环机制
           2.2.1. 事前 -- 风险预判与容量规划 
                      2.2.1.1. 风险地图 (梳理所有履约场景的高风险点,标注影响范围和发生概率)
                      2.2.1.2. 容量预留
           2.2.2. 事中 -- 实时监控与快速响应
                      2.2.2.1. 分级告警：按影响范围将故障分为 P0， P1， P2.
                      2.2.2.2. 根因定位：用 “链路追踪 + 日志分析” 快速定位故障点
                      2.2.2.3. 应急处置：按 “预案优先级” 执行
           2.2.3. 事后 -- 复盘优化与能力沉淀
                      2.2.3.1. 5why复盘
                      2.2.3.2. 方案迭代：将复盘结论转化为优化措施（如 “周末自动扩容规则引擎服务器”），并纳入下次演练；
                      2.2.3.3. 能力沉淀：将共性问题的解决方案标准化（如 “物流 API 熔断降级模板”“资源访问限流配置模板”），形成《履约稳定性手册》，新场景可直接复用。



### 学练机的稳定性治理
>接手时核心矛盾是「技术架构支撑不了业务增长」—— 用户量每周持续新增，但系统是 “大单体（Math 服务耦合 3 个核心域）+ 弱监控 + 无容错”，
> 直接导致1个月内 2 次故障（首页练习目录接口不可用p0故障，影响 60% 日活用户）。 弱监控：我们是有报警通知 报警噪声很大，没人关注； 业务报警指标也不够(三方依赖指标是没有的，基本都是原生的技术指标，核心业务指标很少(比如业务掉底是没有的) ) 
> 我的思路是 “先止血保业务，再系统治存量（含大单体拆解），最后建体系防新增”，形成 “应急 - 治理 - 预防” 闭环。
1. 第一步：现状诊断 拉通团队复盘，明确 4 个核心根因，其中大单体是 “故障放大器”：
        1. 故障响应失效：报警噪声大，无业务报警；
                   报警日均 1200 + 条，但有效率不足 8%（全是 “磁盘使用率 80%” 这类非核心技术指标），真正的 “业务掉底”（如练习提交成功率＜99%）无报警，导致 P0 故障发生后未及时发现；
        2. 架构耦合严重（核心根因）
                Math 大单体包含 “出题、批改、教材管理”3 个核心域，共用 1 个数据库 + 1 个服务进程，
                一旦批改模块因算法依赖超时卡顿，会拖垮整个服务（如 1 次算法接口延迟 2s，导致首页练习目录接口全部超时，触发 P0 故障）；
        3. 容量边界未知：无压测，双 11 压垮 mysql；
                   无压测模型，不知道 “首页接口支撑多少 QPS 会崩”。

2. 第二步：紧急止血  目标是短期内不再出现线上bug，此时暂不拆解大单体（拆解风险高，可能引发新故障），而是通过 “局部优化” 缓解单体压力：
        1. 对齐 P0 接口（首页、出题、批改），
        2. 梳理这些核心接口逻辑，确保所有查询都命中索引，增加redis缓存，兜底逻辑，保证服务不报错。
        3. 给 Math 单体加 “模块级兜底”（如批改模块超时则降级为 “基础结果返回”，不影响出题、教材模块）；
        2. 给单体核心表（如题目表、批改记录表）加索引，缓解数据库压力，首页接口 P95 从 3.2s 降至 600ms；
    结果：1 周内核心接口可用率从 99.8%→99.99%，为后续大单体拆解赢得 “无故障窗口期”。

3. 第三步：系统治理存量风险 。 止血后，用 2 个月做全链路存量治理，大单体拆解是 “架构层面根除故障扩散” 的关键，与监控、数据库治理形成互补：
      3.0. 全面梳理了业务和服务， 画出风险地图， 进行存量风险全面识别。
      3.1 监控与报警治理
           治理报警问题，在业务关键地方增加完善报警日志比如http的出入口，方便问题排查，修改有问题的日志，比如info级别错误写成err。 
           日志接入公司统一报警平台，分级别进行报警，核心业务都是p0级报警， 报警要进行及时处理，报警安排值班。逐步降低报警的阈值。按报警总量大小，环比大小进行。
      3.2 数据库治理
           1. 每日慢sql日报，需要查看并处理掉。该加索引的加索引，该优化逻辑的优化掉。 集群上多个mysql实例，导致集群压力过大，mysql性能降低，对于高负载的实例，单独集群。
           2. 对于mysql 进行扩容，双写方式进行扩容。
           3. 除慢 SQL 治理、集群拆分外，额外按 Math 单体的 3 个业务域（出题、批改、教材）拆分数据库（拆为math_exam_db、math_grading_db、math_material_db）， 
              避免 “单体拆了但数据仍耦合”—— 这是后续单体拆解的 “数据基础”，防止拆解后出现 “跨库调用” 导致的新故障。
     3.3 架构治理：Math 大单体拆解（新增模块，核心体现 “拆解为稳定性服务”）
     3.4 接口性能治理
           按照用户体验耗时的经验参数(100ms无感 1s内流畅 3s内可接受) + 对标竟品的行业基准+ 架构的极限(redis 1ms内， mysql 1-50ms)。对于超过1s的核心接口进行优化，
           先在监控大盘上查看，p95超过1s的接口有哪些，然后查看调用链路，分析占用时长，针对性优化，redis缓存，并发，线程池，业务逻辑优化， 交互优化等(批改异步接口)
           拆解后，可针对单个服务做 “精准优化”（如批改服务原是同步调用算法，拆后改为 “同步返回基础结果 + 异步补全精准批改”，耗时从 2.5s→600ms），避免原单体 “一优化全影响” 的风险。
     3.5 容量与依赖治理（原内容，略，新增 “拆解后的容量弹性提升”）
         容量治理：拆解后可按单服务 QPS 扩容（如双 11 前，仅给批改服务扩容 2 倍实例，QPS 从 8000→1.6 万），比原单体 “全量扩容” 节省 60% 资源，且避免 “扩容不精准导致的浪费 / 不足”；
         依赖治理：每个服务独立配置依赖容错（如教材服务依赖三方接口，拆后单独加降级开关，三方故障时仅影响教材服务，不扩散到出题、批改）。
4. 第四步：搭建预防体系（原内容，略，新增 “拆解后的架构规范预防”）
      4.1. 建立编码与评审规范，上线规范，
      4.2. 完善测试和监控体系，
      4.3. 制定《服务边界设计规范》：明确 “新服务需按业务域拆分，禁止跨域耦合”，避免未来再形成大单体；
      4.4. 代码评审加 “架构边界 Checklist”：评审时必须检查 “是否存在跨服务直接查库”“是否定义了清晰的 RPC 接口”，从源头防止架构回退。
5. 最终成果与沉淀
       稳定性成果：拆后核心服务（出题 / 批改）可用率从 99.99%→99.995%，故障影响范围从 “100% 用户”→“单服务对应域（≤30% 用户）”，全年无 1 次因架构耦合导致的 P0 故障；
       技术沉淀：输出《大单体渐进式拆解指南》，明确 “数据先行、灰度切换、故障隔离” 三大原则，被公司直播课业务线采纳，帮助其拆解大单体后稳定性故障下降 85%。


### 架构治理：Math 大单体拆解（新增模块，核心体现 “拆解为稳定性服务”）
目标：拆解后实现 “模块故障不扩散、单域可独立扩容、容错策略精准落地”，解决原单体 “一挂全挂” 的稳定性痛点。拆解逻辑：按 “业务域驱动 + 渐进式风险控制”，分 3 步落地：
1. 第一步：业务域边界定义（解决 “拆哪里”，避免拆后成 “分布式单体”）联合产品、业务同学用 DDD 梳理，将 Math 单体拆为 3 个独立服务，明确 “故障隔离边界”：

    新服务名	核心职责	稳定性设计重点	依赖关系
    出题服务（Exam-Svc）	生成练习题、缓存题库	需抗高 QPS（首页出题请求占 60%），加多级缓存（本地 + Redis）	仅依赖 “教材元数据”（非实时，超时不影响出题）
    批改服务（Grading-Svc）	接收答题数据、调用算法批改	依赖算法接口（高风险），加 “超时 + 重试 + 熔断”（失败率超 5% 则降级为本地规则批改）	依赖出题服务的 “标准答案”（实时，需做接口兜底）
    教材服务（Material-Svc）	管理教材目录、提供内容查询	静态数据多，加全量缓存，数据库宕机可降级用缓存	无依赖，故障仅影响 “教材查看”（非核心场景）


第二步：数据与代码解耦（解决 “拆得开”，避免数据耦合导致的稳定性风险）

数据解耦：复用 3.2 数据库治理的分库成果，每个新服务仅操作自己的数据库（如批改服务只写math_grading_db），禁止跨库查询；用 Canal 同步历史数据，迁移期间新旧库双写，确保数据一致性（避免拆解导致 “历史批改记录丢失”）；
代码解耦：抽离单体中的公共逻辑（如用户校验、日志）为基础组件，新服务通过依赖引入；定义标准化 RPC 接口（如ExamSvc.getAnswer()），用 Nacos 做服务注册发现，避免代码耦合。

第三步：灰度流量切换（解决 “拆得稳”，避免拆解引发新故障）拆解的核心风险是 “新服务不稳定”，因此采用 “流量逐步切、故障可回滚” 的策略：

灰度 10% 内部用户：1 周内仅让测试 / 运营用户访问新服务，监控 “接口成功率（≥99.99%）、耗时（P95≤500ms）”，发现批改服务因算法超时导致失败率 1.2%，立即触发熔断降级（失败率降至 0.1%）；
灰度 50% 外部用户：2 周内按用户比例切流量，每天切 10%，重点监控 “出题服务 QPS 承载”（原单体 QPS 1.2 万，拆后出题服务独立扛 7000QPS，无压力）；
全量切换：1 周后全量流量切到新服务，旧单体保留 7 天应急回滚，期间无 1 次稳定性故障，最终下线旧单体。

### math服务在处于快速迭代中，是怎么保证项目拆分和新需求耦合的问题呢
> 在 Math 服务 “快速迭代（2 周 1 个版本）” 与 “单体拆分” 并行的场景下，核心挑战是避免 “拆分进度被需求打断” 和 “新需求引入新耦合”—— 本质是平衡 “短期业务交付” 与 “长期架构解耦” 的优先级。
> 我们的解决方案不是 “先停迭代再拆分”，而是通过「需求管控 + 技术规范 + 拆分节奏设计 + 团队对齐」四套机制，让 “拆分和迭代互为支撑”，而非互相冲突
